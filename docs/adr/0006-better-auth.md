# 0006: Better Auth for identity and organizations

Status: accepted (2026-09-16)

## Context

A standalone Braivo installation needs to know who is signed in before it can do anything useful: content owners administer content, learners accumulate evidence against their own identity, and both are product concepts defined in `product.md`. Authentication is not the product, and building it is not a good use of pre-PMF time.

Content owners also work in groups — a school, a training provider, a team inside a company — so content and learners need an ownership boundary even with no managed service involved.

## Decision

Use **Better Auth** (MIT) with its organization plugin, in `braivo`, against the PostgreSQL database from [ADR 0005](0005-postgresql-drizzle.md) through its Drizzle adapter.

- `api` mounts Better Auth's handler. Application code receives the resolved identity as plain data; `learning` never sees it, per the dependency rules in `architecture.md`.
- Better Auth's tables are generated by its CLI into their own file, `packages/db/schema/auth.ts`, which the Drizzle config includes alongside the hand-written schema. The CLI overwrites its output file, so generated tables never share a file with domain tables.
- The CLI only generates; nothing it produces reaches a database on its own. Every schema change, Better Auth upgrades included, is applied as a committed Drizzle migration ([ADR 0005](0005-postgresql-drizzle.md)). One database, one migration history, no second migration runner.
- `schema/auth.ts` is generated and committed, never hand-edited, and regenerated with the tooling version this repository pins — otherwise the same commit yields different tables on different days. Additional fields on Better Auth's tables are declared in the Better Auth config and regenerated, so config and schema change together.
- `better-auth` and its CLI are pinned to exact versions rather than ranges. The committed `schema/auth.ts` and the migration generated from it describe one version's tables, so a range would let an install resolve a Better Auth whose expectations the shipped migration does not meet.
- **Organization** is therefore a product concept in `braivo`, not a Braivo Cloud one. It answers "who owns this content and these learners" for a standalone installation.
- Organization context from a request or session is not authorization. A workflow verifies the actor's membership and permission for an organization before reaching its data. Passing an `organizationId` explicitly, as `architecture.md` requires, only removes hidden state; it says nothing about whether the actor was entitled to that organization, and confusing the two is how cross-organization data leaks happen.

How a Braivo Cloud tenant relates to an organization, and how tenant data is isolated in storage, stay open. Organizations exist because a standalone install needs them; adopting one as the tenancy boundary is a separate decision with its own trade-offs, and nothing here presumes it.

## Consequences

- Sign-in, sessions, and organization membership come with the product rather than being reimplemented, and self-hosters get them without configuring an external identity service.
- Treat a Better Auth upgrade as possibly schema-bearing: regenerate, read the schema diff and any migration it produces, and commit them together. The CLI is the `auth` package, released alongside `better-auth` at the same version.
- Better Auth is MIT, so it composes with Braivo's AGPL ([ADR 0002](0002-agpl-only.md)). Identity is server-side: a client talks to the API with whatever credential the API defines.
- Braivo's own authorization rules are built on organization membership. Whether its roles are enough, or product-specific roles are needed, is decided when the first rule needs them.
- Better Auth owns endpoints that write across several of its tables, and its Drizzle adapter does not use transactions unless told to. Deleting an organization removes its members and invitations before the organization itself, so a Braivo foreign key refusing that last step left the organization standing with every member gone, the owner included. Better Auth runs that delete in the adapter's transaction, so the adapter is configured with `transaction: true`. That buys atomicity for this endpoint, not for every Better Auth write, and whether the delete still runs in a transaction is worth re-checking on upgrade. Taking a library's endpoint means taking its write order too, and any Braivo constraint that can refuse part of one is a data-loss bug until the whole is atomic.
- **An organization that still owns objectives or courses cannot be deleted.** The schema already refused it — both tables restrict the delete, because dropping an organization is not a licence to destroy the history its learners built — but a constraint can only refuse, and the answer reached the caller as a 500 naming a PostgreSQL constraint. A `beforeDeleteOrganization` hook states the rule instead, as a 409, before the organization's own rows are touched. The constraints stay underneath as the guarantee: the check and the delete are not one step, so content created in between still lands on them. Better Auth clears the caller's active organization before that hook runs and a refusal does not restore it; the caller selects it again rather than Braivo reaching past the plugin. There is deliberately no cascade that would destroy the content along with the organization.
