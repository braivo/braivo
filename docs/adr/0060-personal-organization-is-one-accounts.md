# 0060: A personal organization is one account's, alone

Status: accepted (2026-11-08); amends [ADR 0018](0018-sign-in-and-invitations.md) (setup's limit, invitations), [ADR 0028](0028-original-files.md) (a store deletes), [ADR 0046](0046-material-in-steps.md), and [ADR 0053](0053-learners-data.md) (erasure's reach)

## Context

ADR 0046 keeps a learner's own material in an organization of their own, with every content owner's action and no personal content model: "an organization of one already is one". [ADR 0059](0059-own-learn-app-on-the-installations-origin.md) gives its courses a home, My learning. A flag set at creation, one per account under a lock on the account, would record _that_ an organization is personal, not _whose_, and the lock would guard setup alone. Other writers would break both:

- The operator's `organization make-owner` promotes any member: Bob, an admin in Alice's personal organization, made its owner, would own two personal organizations, and setup would answer whichever it found first.
- Invitations other than a learner's need no learn domain: Alice could invite Bob as an admin, and Alice's courses would appear among Bob's own in My learning, with every learner's progress there his to read.
- Erasing an account refuses an organization's only owner ([access](../specs/access.md), access-49), so setting up a personal organization would take away the person's way to erase their account.

## Decision

- **`organization.personal_owner_id` says whose personal organization it is:** a nullable foreign key to `user`, unique, `ON DELETE RESTRICT`. Null for every other organization. Braivo sets it at creation and nothing changes it; Better Auth takes it as no input. The API keeps `personal`, a boolean derived from it, and names the owner only where a caller needs it. The unique index alone holds one per account: setup inserts the organization and its owner's membership in one transaction and, on conflict, answers the one the account has (201, then 200), so no lock.
- **Its owner's membership stays, written with it.** Every access check and Better Auth read membership as in any organization; `personal_owner_id` decides whose it is, and a membership row never redefines it.
- **No one else joins it, and the database says so.** A trigger refuses a `member` row in a personal organization for anyone but `personal_owner_id`, and an `invitation` to one at all, so every writer is held: Better Auth's invitations and their acceptance, the operator's add-member, which Better Auth runs, and make-owner, which Braivo's persistence runs, and whatever is added later. Braivo's use cases and Better Auth's hooks refuse first, `PERSONAL_ORGANIZATION`, so a person reads a reason rather than a database error. Removing or demoting its owner is refused already, as for any only owner (access-56). With one member, its console shows no Members, Groups, or Domains.
- **An account may own a school and a personal organization, in either order.** Setup's limit of one owned organization (access-31, `ALREADY_OWNER`) counts schools alone.
- **Its person sets it up explicitly:** `POST /api/organization-setup` `{ "personal": true }`, from the account's browser session alone, never a tool. Visiting `/learn` creates nothing.
- **Erasing the account erases its personal organization:** everything it holds, its AI usage rows included, deleted before the account's row in the account's erasure, shown with its counts before confirming, and named in its record ([ADR 0053](0053-learners-data.md)). By the rule above it holds that person's material and history alone, so nothing another person relies on goes with it. Its files' bytes, under the organization's own prefix in the store and shared with no other organization, go after the database commits, by a delete ADR 0028's store gains: a failure leaves bytes nothing names, never a row whose bytes are gone. An upload holds the organization's row (`FOR KEY SHARE`) from its authorization through writing the bytes and recording them, taken before it touches any file row; the erasure takes the same row `FOR UPDATE` before it reads what it erases or deletes anything. So the erasure waits for an upload under way and then erases what it recorded, and an upload arriving meanwhile waits, then finds no organization and writes nothing; an upload whose connection is lost while it writes, so its hold with it, empties the prefix itself once its write has ended, stored or failed, if it then finds the organization gone, as an organization's ID is never reused. A personal organization set up while the erasure locks is refused, as made since it was shown. An upload straight to the store, if one comes, bounds the same race its own way first. The record is done only once the database holds the erasure (`account_erasure`, ADR 0053) and the prefix is empty. Until then it is pending, and running the erasure again for that email resolves it first, bound to the record's own IDs, never the email's current account: it waits on the recorded account's row, which a running erasure holds, so one still under way finishes before it is judged; committed, its prefix is emptied and the record done; not found committed, it is kept until an erasure of that same account commits and supersedes it, since a restored database lacks a marker that did commit. A record with no account locks no row, so only its marker closes it (access-49). An erasure that may need a personal organization's files deleted is refused without the store that holds them: rows cannot say no bytes were stored. Only then does the command consider the email's account, a later registration included, as any erasure, confirmed afresh. After a restore, ADR 0053's replay governs instead. An ordinary organization's only owner is still refused.
- **Nothing outside it grants access to it:** not a role in a school, not any other organization's membership. Material meant for others lives in an ordinary organization. A learner adds nothing to a school's organization (ADR 0046).

## Alternatives rejected

- **A `personal` boolean, with a lock per account.** Says that, not whose; the lock guards setup but not make-owner.
- **A `kind` column beside an owner column.** Two values kept consistent by a check, for kinds nothing needs yet.
- **The owner's membership as the identity.** A role anyone with authority may change would decide whose material it is.
- **A personal organization shared by invitation.** Membership enrolls in every course and gives an admin every learner's progress, far wider than the reader of "your own material" expects.
- **Personal setup on its own endpoint.** `{ "personal": true }` on setup is serviceable, and a second route adds nothing.
- **Keeping the erasure refusal until a separate closure flow.** Whoever set one up could not erase their account without the operator, for material no one else may hold.
- **A personal organization inferred**, as the organization someone owns alone (moved from ADR 0059). A school's sole owner would see the school as private material.
- **A personal organization made on first visiting `/learn`**, or with the account (moved from ADR 0059). An organization nobody asked for, for everyone who signs in, and a write behind a page that only reads.
- **The guard in each writer alone.** Better Auth's hooks miss make-owner, which bypasses Better Auth, and Braivo's use cases miss add-member, which Better Auth runs; a new writer would have to remember it.
- **One owned organization of any kind**, as setup counted before (moved from ADR 0059). A school's owner could never keep material of their own, and someone with their own could never set up a school.

## Consequences

- Setup's eligibility (access-31) counts the schools an account owns, not every organization.
- Account erasure (access-49) reaches a personal organization's content and file bytes, which ADR 0053 left with the organization; the file store gains a delete by prefix and a listing beside `put` and `get` (ADR 0028), for every store an installation configures, the erasure log's included, so pending records are found.
- Done in this repository: `personal_owner_id` and its uniqueness, setup inserting organization and owner with no lock, the trigger and its refusals, lookup by owner, and the hidden console pages (access-60); the store's listing and delete by prefix, the upload's transaction, and erasure reaching a personal organization, with recovery of a pending record (access-49).
- An upload holds a database connection while it writes up to 50 MB to the store. [ADR 0034](0034-node-postgres.md)'s trial on Workers with Hyperdrive did not reach the file stores, so whoever serves the API there measures one upload at that limit before relying on it.
- A database lock cannot fence a store's write once its connection is lost: an upload that loses it mid-write and then crashes, or cannot reach the database, before finding its organization erased leaves bytes nothing names, under the erased organization's prefix. Rare (a lost connection, then a crash or an outage, during that person's own erasure) and found by listing prefixes whose organization is gone.
- A run that found a pending record of another account than the email names now asks for the email typed back even with `--yes`, as the address may be a later registration's.
