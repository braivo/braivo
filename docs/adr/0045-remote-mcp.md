# 0045: Braivo's MCP server is `/mcp`: the API as tools, in-process, as an OAuth connection bound to one school

Status: accepted (2026-10-14). Amends [ADR 0022](0022-machine-access.md). Supersedes [ADR 0023](0023-mcp-server.md) (2026-10-19): `braivo mcp` is retired, and the decisions of it still in force are stated here.

## Context

Teachers are to reach Braivo from the AI they already use, hosted Claude or ChatGPT, by adding a URL and signing in ([product.md](../product.md), core job 1), and content owners to turn material into courses with it, at their own AI's cost rather than with credits in Braivo's cloud. Those clients take tools over the Model Context Protocol. A local server over stdio, `braivo mcp` ([ADR 0023](0023-mcp-server.md)), reached only agents that run local programs, with the whole account's session from `braivo login` ([ADR 0022](0022-machine-access.md)). Hosted clients speak MCP over HTTPS and authorize by OAuth, and desktop agents such as Claude Code connect to such a server too: Claude registers itself with a client ID metadata document (CIMD) or a pre-registered client, ChatGPT by CIMD, dynamic registration, or a client its developer provides. MCP's 2026-07-28 revision is stateless. A spike serves one tool at `/mcp` with Better Auth's OAuth provider; a real client has completed its whole flow against it.

What an assistant reads may carry instructions (Consequences), and a teacher's connection reaches material learners study and, with a school's consent, learners' progress, minors' included.

## Decision

- **One MCP server, `/mcp`; the CLI serves none.** Hosted assistants and desktop agents connect to it alike. A desktop agent runs [`braivo`](0027-standalone-cli.md) beside it for what takes the machine, such as adding a local file's text with its original ([ADR 0028](0028-original-files.md)).
- **Tools are the API.** `createMcpServer(client, version, …)` (`apps/server/mcp`) takes Braivo's API client, whose requests enter the server's own routes in the same process, as the connection. `list_organizations`, `add_source`, `cite_sources`, `author_tasks`, `create_course`, and the rest each make one call of it, and a write answered with a review link one more, to find the organization's slug. Every rule, refusal, idempotency key, and record is the route's; no tool decides anything the API does not, so an agent is held to exactly the console's rules, and a rule added to the API reaches it without a change here.
- **The citation check is the feedback loop.** The server's instructions tell the agent the workflow and that every quote is checked. When Braivo refuses a quote, the tool answers with Braivo's own reason as an error result — "Citation 2: the quote occurs more than once in the source; quote more of it" — which the agent reads and corrects, rather than a protocol failure it cannot. The client carries a 400's `{ "error" }` as `BraivoError.reason` for this.
- **The official TypeScript SDK**, `@modelcontextprotocol/server` (its 2.x line), MIT-licensed, with Zod for tool schemas: the protocol is young and moving, and the SDK is where its changes land first. Stateless: a server per request, no protocol session, nothing held between calls but stored objects. MCP 2026-07-28 alone; an earlier revision is added only if a supported client is seen to need it.
- **One endpoint per installation**, `BRAIVO_URL/mcp`, served by the API's process; its token's audience is that URL, and no other route accepts it.
- **A connection is an OAuth grant to one client, for one school.** Better Auth's OAuth provider issues it after sign-in and a consent page naming the client, the school, and what it may do. The school is chosen there, among those the person may author in ([ADR 0048](0048-author-role.md)), or created there through the existing operation where the installation offers self-serve ([access](../specs/access.md), access-31), the authorization resuming after. Each grant is stored with its own identity, bound to one person, client, and school, so two grants of one person and client for two schools are independent: disconnecting one leaves the other working. Every call resolves its token to that stored grant, so disconnecting in the console refuses the next call while its access token still verifies; the token carries the school as a locator, never as authority. Roles and memberships are read per call, as for every credential. `list_organizations` answers the connection's school, the assistant's way to learn its ID. An `organizationId` a tool takes must be that school, and every course, source, task, or other resource a call references, by its ID alone or beside one, is checked against the grant by the organization that owns it; an argument never establishes ownership.
- **Two scopes, split by sensitivity:** `braivo:author` (sources, objectives, tasks, courses) and `braivo:progress` (whatever names learners or reads their progress, `list_groups` included, also behind the organization's own setting). First consent asks for `braivo:author` by default, never for learners' data; a person who only teaches groups is not made to grant authoring they cannot use, by a means chosen once clients' scope requests are observed. `list_organizations` answers with either scope. A client that supports step-up asks for `braivo:progress` when a tool needs it; one that does not reconnects with it; neither gets learners' data without that consent. A call lacking one is answered before the tool runs with `403` and `WWW-Authenticate: Bearer error="insufficient_scope"` naming that scope alone; a missing membership or role is the tool's error, never a new consent.
- **A connection is a token** for [ADR 0022](0022-machine-access.md) and [ADR 0039](0039-published-in-the-console.md): its writes wait for review, it never publishes or retires a published task. The server tells it from a browser and from a device-flow token by its credential, not by a header: the in-process request carries its principal in server memory, which no network request can claim.
- **Client identity.** A client ID metadata document, and any `jwks_uri` it names, is fetched only where private addresses are refused, following no redirect: on Bun, through a transport that resolves once, refuses special-use addresses, and connects to the address it checked, as Better Auth's CIMD contract requires; on Workers, through the runtime's `fetch` with the `global_fetch_strictly_public` compatibility flag, which routes it through Cloudflare's public routing, never straight to a zone's origin past its security settings. That rests on Cloudflare's network refusing private destinations, as its own OAuth provider does: undocumented as a guarantee, but observed from a deployed Worker on 2026-10-14, refusing addresses written as hosts, names resolving to private addresses, and redirects to either. On Workers, Better Auth's own limits and cache, held per server, last one request, so the host limits fetches across requests itself: at the edge, or around each fetch with `wrapClientMetadataFetch`, a trusted wrapper whose network calls still go through the fetch it was given. A host may fetch nothing instead and support the clients it pre-registered, no others: a hosted client is registered under its document's URL, its redirect URIs copied from that document; CIMD is still advertised, and `private_key_jwt` withdrawn, so ChatGPT and Claude send that URL as a public client rather than ask a teacher for a client ID; an unregistered URL is refused. A public client ID does not authenticate the client: registered redirect URIs and PKCE protect the authorization flow, and the teacher consents to the access asked for; the consent page names the client without claiming its publisher is verified. No dynamic registration.
- **Keys on another origin.** Better Auth takes a document's `jwks_uri` only on the document's origin or a trusted one, and the installation's alone is trusted; Gemini's documents on `accountlinking.google.com` name keys on `www.gstatic.com`. Better Auth is shown that `jwks_uri` as an alias on the document's origin, which the fetch it reads keys through maps to the real one (`aliasGoogleJwks`), until Better Auth can allow the pair itself ([better-auth#11916](https://github.com/better-auth/better-auth/issues/11916)).
- **The outer edge:** host and `Origin` checks, a body limit fitting the largest legitimate tool call, not a file (files come in through upload and are referenced by ID), `no-store`, limits per person and client, and records of client, person, school, tool, and outcome, never content.

## Alternatives rejected

- **Tools over the application's use cases**: the API's contracts written a second time, and the credential that acted lost.
- **Calling the API over HTTP with an internal token**: a network hop and a credential to guard, for what in-process dispatch gives.
- **A separate MCP Worker or service**, and the bearer endpoint for session tokens braivo-cloud built and dropped: a second trust boundary and deployment, or a browser session's authority in a third party's configuration.
- **An account-wide grant**: one consent reaching every school a teacher is in, so one mistaken call reaches another school's learners. A client that cannot hold one connection per school is a separate decision, not a fallback.
- **Scopes per tool or verb** (`read`/`write`/`publish`): reading courses is not the risk, reading learners is; publishing is not a scope ([ADR 0039](0039-published-in-the-console.md)).
- **Checking a client's DNS, then fetching by name**, or fetching only from a list of known hosts, on a runtime that neither pins nor routes strictly public: a rebinding between check and connection reaches what the check refused, and a document's `jwks_uri` escapes any list of client ID hosts.
- **Trusting a client's key origin** (`trustedOrigins`) for a `jwks_uri` elsewhere: Better Auth would trust it for sessions and redirects too.
- **Inlining keys from another origin in the document** instead of an alias: Google's already take most of Better Auth's 5 KiB limit on a document, and inlined keys are never refetched for a key they lack.
- **Dynamic client registration**: unbounded clients for no client that needs it.
- **Only pre-registered clients on Workers** (replaced): each new client, and each change to its redirect URIs, waits for the operator. Kept as a mode for a whole installation, to return to if a client's document cannot be fetched.
- **Not advertising CIMD on Workers** (replaced): ChatGPT then asks each teacher for a client ID, and Claude, finding no registration endpoint either, cannot connect.
- **A "current school"** held by the connection beside the tools' arguments: hidden context an agent gets wrong.
- **A local server over stdio, `braivo mcp`** (replaced): a second way to serve the same tools and keep them working, acting with the whole account's session in every school rather than a grant for one school that the console disconnects; desktop agents reach `/mcp` instead.
- **A hand-written JSON-RPC loop** instead of the SDK: less code at first, and a standing obligation to track the protocol by hand.

## Consequences

- Drafting happens in the person's own AI app and at their cost; Braivo sees only the results, and verifies them. A draft by Braivo's own model ([ADR 0029](0029-server-drafting.md)) is accepted through the same endpoints.
- Tool inputs are validated twice: by the tool's schema, which catches a malformed call before a request is made, and by the API, which is the one that counts. A new task kind is a new variant in `content` and in `author_tasks`' schema.
- The server's `instructions` and tool descriptions are prompts, version-controlled beside the code that uses them, as the architecture asks.
- `read_source` hands the agent a source's text, which may carry instructions of its own — a transcript saying "ignore your task", say. Braivo cannot tell text from instruction, and does not try. What bounds the damage is that the connection acts as the person and nothing more, in the one school granted, where they author ([ADR 0048](0048-author-role.md)), over the same API and checks as the console; the agent's own client is where a person approves what it does.
- No tool reads learners' names or progress until `braivo:progress` exists; until then, they are read in the console.
- [ADR 0022](0022-machine-access.md) gains a third credential, the connection, beside the browser and the device flow; only routes that must tell them apart read which.
- A teacher working across schools connects once per school where the client supports it, or reconnects to switch; each supported client's behavior is verified before release. A client's own profile convention (ChatGPT's) gets a small tool answering the grant's school if it needs one.
- Material reaches remote tools as bounded text; no tool takes a file path. A file comes in through the console's upload, or `braivo sources add --original` on the person's machine, and becomes a source there, which the assistant then reads by pages; no tool lists files or tells the person where to upload. [ADR 0046](0046-material-in-steps.md) (accepted, not built yet) gives remote tools the file channel.
- In Cloud, `/mcp` and the OAuth discovery paths route to the API Worker.
