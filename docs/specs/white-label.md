# White-label

Status: living; checked against the code on 2026-10-11.

Each organization's learners use the learn app on the organization's own hostname, which wears its name and serves its courses alone; its content owners manage it in one console at `braivo.app/<slug>` (product.md, core job 6). Which hostname serves which organization is a database row, not configuration.

Each app calls `/api` on its own origin; which hostname reaches which app and the API is the deployment's routing (see Boundaries):

| Origin                                           | Serves                                                | Session                         | Hostname controlled by |
| ------------------------------------------------ | ----------------------------------------------------- | ------------------------------- | ---------------------- |
| `BRAIVO_URL` (`braivo.app` on Cloud)             | Console at `/`, sign-in, `/api`                       | The account's, host-only cookie | Operator               |
| An organization's domain (`acme.braivo.app`)     | That organization's learn app, `/api`                 | A learner session, handed over  | Operator               |
| A customer's own domain (`learn.school.example`) | The same                                              | A learner session, handed over  | Customer               |
| `www.braivo.app`                                 | Marketing, Braivo Cloud only, outside this repository | None                            | Braivo                 |

## Rules

- **white-label-1:** A hostname serves at most one organization, held by the database too, even against concurrent registrations; an organization may have several learn domains, each serving its learn app, its sign-in included, with sessions of its own. The latest registered is the one its learn domain is named by (`learnDomain`, access-25); registering an earlier one again changes nothing. So a custom domain added after `<slug>.<self-serve domain>` is named, and the subdomain still serves when the custom one does not. Deleting an organization deletes its domains: the hostname is no longer trusted, and another organization may register it. `apps/server/application/domains.test.ts`, `apps/server/auth/origin.test.ts`
- **white-label-2:** The operator registers a domain with `braivo organization add-domain --slug <slug> --hostname <hostname>`; self-serve setup registers `<slug>.<BRAIVO_SELF_SERVE_DOMAIN>` alike (access-31). The hostname is stored lowercased and must be what `URL#hostname` gives back, or no request's host would match it: ASCII labels of letters, digits, and inner hyphens, 1 to 63 characters each, 253 in all; no scheme, port, path, trailing dot, or IP address; an internationalized name in its `xn--` form. Public DNS is not required (`training` qualifies). The database refuses a hostname in capitals. `apps/server/application/domains.test.ts`, `apps/server/auth/origin.test.ts`
- **white-label-3:** Registering refuses `BRAIVO_URL`'s hostname, whatever its case, which reaches every organization whatever its row says; a slug no organization has; and a hostname another organization has, naming it. The same mapping again succeeds, at once or later, so provisioning may retry; another hostname for the same organization is added (white-label-1). `apps/server/application/domains.test.ts`
- **white-label-4:** The host a request was sent to is a ceiling on which organization a course route reaches: on `BRAIVO_URL`'s host, any; on an organization's domain, that organization alone; on any other host, none, so deleting a domain's row revokes access rather than widening it. It grants nothing. When the request has a session, a course outside the ceiling answers exactly as a missing one, 404, so a domain learns nothing about other organizations. The course routes are a course's `…/next`, `…/activity`, and `…/attempts`, and a learner's progress report; a course's overview is read on the installation's host alone (progress-12), and `GET /api/courses` lists a domain's own courses alone (learner-loop-2). On a host that is neither, no session holds either, so what each route answers there is in `apps/server/api/index.ts`. `apps/server/api/learning.test.ts`, `apps/server/application/learner-in-course.test.ts`, `apps/server/application/activity.test.ts`
- **white-label-5:** `GET /api/organization`, needing no session, answers the name of the organization the request's host serves, or 404 when it serves none, with `Cache-Control: private, no-store`. `apps/server/api/app.test.ts`
- **white-label-6:** The learn app reads that name before sign-in, shows it, and uses it in the page title. With an organization named `Fernwood`, the title is `Fernwood`, or `Spanish · Fernwood` on a course named Spanish; on a host serving no organization, those titles are `Learning` and `Spanish`. A failure to read the organization leaves the app unbranded rather than down. `apps/learn/routes.test.tsx`
- **white-label-7:** The console's URL names the organization, never the session: Better Auth's active organization is unused. `/<slug>` is resolved among the organizations the user manages: a slug they do not manage reads as not found, and a path below one they manage that names no page says only that there is nothing here. `/` signed in opens the organization last opened in this browser while the user still manages it, else the first they manage, by name, else `/join`; `/join` itself opens the same for someone managing one who may not set one up (access-31). Managing several, or offered setup, the header's switcher beside the organization's name lists them by name, the one shown marked, each opening its home, and last, where offered, "Set up an organization"; there is no page listing them. `apps/console/routes.test.tsx`

| Path                                                          | Page                                                                                                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`                                                           | Signed in: as white-label-7 says. Anonymous: `/login`                                                                                                |
| `/join`                                                       | Setting up an organization, for whoever owns none (access-31); managing none, where learners go instead                                              |
| `/device`                                                     | Approving a content owner's tool, by the code it showed ([access](access.md))                                                                        |
| `/consent`                                                    | Approving an AI app's remote MCP connection, by Better Auth's signed request                                                                         |
| `/<slug>`, `/<slug>/courses/<course>`, `…/learners/<learner>` | The organization's console                                                                                                                           |
| `/login`                                                      | Sign-in ([access](access.md))                                                                                                                        |
| `/<slug>/settings/<page>`                                     | The organization's settings: `account` and `preferences` (access-36), `general` (access-37), `members` (access-26), `domains` (white-label-9 to -12) |

- **white-label-8:** A slug is lowercase letters, digits, and single hyphens, at most 63 characters, and none of the reserved `api`, `assets`, `consent`, `device`, `invitations`, `join`, and `login`, which `/<slug>` would shadow; every root-level console route is reserved. An organization is never created with a malformed or reserved slug, and its slug never changes: an update naming a different one is refused, the current one resent accepted. `apps/server/auth/slug.test.ts`, `apps/server/auth/auth.test.ts`
- **white-label-9:** `GET /api/organizations/:organizationId/domains` lists the hostnames serving an organization, newest first (registration time, then hostname, both descending), the first the one its learn domain is named by, then those it claimed (white-label-10), and whether the installation can add one, to its `owner` or `admin` alone; the console's `/<organization>/settings/domains` shows them, each a link, the first marked Primary, or, with none, that learners have no site yet. `apps/server/application/domains.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/api/policy.test.ts`, `apps/console/routes.test.tsx`
- **white-label-10:** An organization's `owner` or `admin` claims a hostname with `POST /api/organizations/:organizationId/domains` on an installation passing `createServer` a provisioner ([ADR 0038](../adr/0038-self-served-custom-domains.md); without one, 501): the hostname, lowercased, is stored as a claim with an identity of its own, a later claim's to a hostname greater, and the provisioner is asked to serve it for that claim once proven (whatever an earlier claim to it left never proves this one), answering the DNS records to create; each listed claim's status is read from it live (unread, `null`). A claim serves nothing, is trusted as no origin, and leaves the learn domain as it was. Refused, claiming nothing: a hostname white-label-2 refuses, the installation's, the self-serve domain or one under it, one another organization serves or claimed (never saying whose), and one this organization serves. Claiming its own claim again asks the provisioner again; a provisioner failing answers 502 and keeps the claim. A hostname is one organization's across domains and claims, concurrent claims and registrations included, under a lock on the hostname; the operator's registration of a hostname its organization claimed replaces the claim, and of one another claimed is refused, naming it. A claim not activated within seven days expires: no longer listed, it holds the hostname no more, and the hostname's next claim, by any organization, or the operator's registration replaces it, a new claim proven afresh. The console's Domains page lists each claim under Not active yet, saying it is dropped seven days on unless activated, with a badge (Pending, Verified, or Status unknown) and its records (Type, Name, Value, each name and value with a button copying it), or that they are not available yet. Where the installation can add one, a form adds one: a blank domain refused before it is sent, each refusal worded from its code, one the provisioner failed for said to be saved, for adding it again to retry; locked while sent, given up after 10 seconds; nothing pending carried to another organization's page. `apps/server/application/domains.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/api/policy.test.ts`, `apps/console/routes.test.tsx`
- **white-label-11:** `POST /api/organizations/:organizationId/domains/:hostname/activate`, by the organization's `owner` or `admin` on an installation with a provisioner (without one, 501), asks the provisioner where the organization's own unexpired claim to that hostname stands and, once it reports it ready, moves it, under the hostname's lock, from claims to the domains serving the organization, the newest, so its primary; a hostname serving it already succeeds without asking, left as it is. Not ready: 409 `NOT_VERIFIED` with its status, the claim kept; no such claim (another organization's, expired, or none): 404, the provisioner not asked, so no organization learns where another's stands; the provisioner failing: 502, the claim kept. Two activations at once activate once, both succeeding; a proof read for a claim that expired and was claimed again meanwhile activates nothing (404). Where the installation has a provisioner, the console's Domains page gives each claim Check and activate, or Activate once Verified: activated, the domain is listed first, Primary, its link focused, a status saying it now serves learners; not ready yet, an alert saying to try again in a few minutes, a new one each time, its records read again; locked while checking. `apps/server/application/domains.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/api/policy.test.ts`, `apps/console/routes.test.tsx`
- **white-label-12:** `POST /api/organizations/:organizationId/domains/:hostname/remove`, by the organization's `owner` or `admin` on an installation with a provisioner, removes a domain serving it, or its claim to one: it stops serving there and then, its learner sessions deleted with it, those a sign-in under way opens too, so adding it back opens nothing for them (access-17), the primary falling back to the next newest; then the provisioner is told to forget that claim alone, so a later claim to the hostname is never touched (a domain the operator registered, nothing), waiting for it at most 5 seconds, within the console's 10, its failure or silence logged, not refused. Refused, asking it nothing: the installation's own hostname and the self-serve domain's, which setup gave, 409 `DOMAIN_RESERVED`; the only domain serving the organization, 409 `LAST_DOMAIN`, held under a lock on the organization, so two removals at once leave one; a hostname the organization does not hold, 404. `GET …/domains` marks each domain `removable` accordingly. The console's Domains page offers Remove, named for its domain, on each removable domain and each claim, asked first in a dialog saying what stops; while removing, focus is back on Remove, which says Removing… and opens nothing; removed, the page says so and focus moves to its heading; refused, an alert says why. `apps/server/application/domains.test.ts`, `apps/server/application/learner-sessions.test.ts` and `apps/server/api/learner-sign-in.test.ts` (a sign-in under way), `apps/server/api/client.contract.test.ts`, `apps/server/api/policy.test.ts`, `apps/console/routes.test.tsx`

## Boundaries

- Who may sign in, hold a learner session, and reach which route, and which request origins are trusted: [access](access.md). Those checks consult the hostname-to-organization mapping this spec owns; the host ceiling never grants, and access decides within it.
- What a learner's course routes do: [learner loop](learner-loop.md); a learner's report and a course's overview: [progress](progress.md).
- DNS, TLS, and which app each host serves stay the operator's: the server answers `/api` alone and reads the organization from the request's `Host`, which a proxy in front must pass. Only SQL replaces or removes a domain.
- Not here yet: branding beyond the name, changing a slug, and moving an organization to another hostname (see Gaps).

## Decisions

- [ADR 0004](../adr/0004-one-application-origin.md): origins, console at `/<slug>`, the host ceiling, several domains per organization, named by the latest, the organization's own domain allowed, marketing on `www`.
- [ADR 0018](../adr/0018-sign-in-and-invitations.md): learner sessions per learn domain, which admit customer-owned domains.
- [ADR 0038](../adr/0038-self-served-custom-domains.md): organizations add their own domains, verified by the installation's provisioner, serving only once activated.
- [ADR 0016](../adr/0016-route-files.md): route files, including `$organizationSlug/route.tsx` as a layout.

## Gaps

| Gap                                                                               | Impact                                                                   | Next step                                                                          |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Slugs cannot be changed                                                           | A typo in a slug is permanent without SQL                                | Owner or admin rename with the warning (ADR 0004)                                  |
| Branding is the name only                                                         | Weak white-label: no logo, colours, or favicon                           | A branding slice: which fields, where stored, how the learn app loads them         |
| An installation without a provisioner adds and removes domains by command and SQL | Self-hosters move an organization by hand                                | A provisioner of their own (ADR 0038), or commands when one is needed              |
| The operator cannot cancel a claim                                                | A hostname claimed by the wrong organization waits up to seven days      | A command, having checked who asks (ADR 0038)                                      |
| No limit on an organization's pending claims                                      | Each claim costs a provisioner call, and each listed claim a status read | A limit, and rate limiting, before claiming is open to any organization (ADR 0038) |
| No deployment packaging for multiple hosts                                        | Self-hosters must build their own proxy that passes `Host`               | Deployment docs or packaging (README, Deployment)                                  |
