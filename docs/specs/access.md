# Access

Status: living; checked against the code on 2026-10-11.

How people sign in, and what they reach once in: learners, content owners, and content owners' own tools. Every core job needs it, and signing in on an organization's own domain is part of core job 6 ([product.md](../product.md)). Whoever proves an email has an account, and an account alone reaches nothing: what a person may see or do in an organization follows from their membership in it and the organization roles it carries. Who a request acts for comes from its session or token; what they may reach in an organization comes from their membership there, never from a user or organization the request names.

## Rules

A status named below is that rule's refusal, not a route's whole status contract; `apps/server/api/index.ts` lists each route's statuses. Where several refusals apply, which one answers is left unspecified.

### Accounts and sign-in

- **access-1:** An account is made, and signed in to, with a code sent to its email ([ADR 0018](../adr/0018-sign-in-and-invitations.md)), in the language localization-6 chooses, or with Google (access-30). A code is six digits, good once, for ten minutes and five guesses, stored so that only the installation's secret recovers it (encrypted on the installation's host, as a seed it derives the code from on a learn domain, access-32): a database leak yields no live code. A code sent back that is not six digits is refused, `400` `INVALID_OTP`, unchecked; one that cannot be recovered (stored before, or under a secret since replaced) is refused, and replaced when asked for again. Every address gets a code, so asking says nothing of whether an account exists; the first sign-in makes the account, verified, named by the request's `name` if it sends one (the console names it just after, access-5), and every later one signs in to the same account. No password makes an account. One opens only an account `BRAIVO_REVIEWER_EMAILS` lists, an app directory's reviewer, with the password the operator set (`reviewer set-password`, at least 16 characters); a wrong password and an unlisted account's, whatever is stored, are refused alike, `401`, and in production each client gets ten tries a minute, counted per server process, as all of Better Auth's limits are (a deployment of many needs a limit in front, [deployment](../guides/deployment.md#before-you-expose-it)). The console takes it at `/login?method=password` alone, which nothing links (an account without a name is named first, as after a code), and continues as a code's sign-in does, an OAuth authorization included (access-40); learn domains never. A password too long for Better Auth is refused the same way, listed or not. Nothing over HTTP signs up with, sets, changes, resets, checks, or unlinks a password (`404`); `reviewer remove-password` deletes it and ends the account's sessions, even if it is already gone. `apps/server/auth/auth.test.ts`, `apps/server/api/reviewer.test.ts`, `apps/server/api/mcp.test.ts`, `apps/server/cli/index.test.ts`, `apps/console/test/sign-in.test.tsx`
- **access-2:** Only sign-in codes are sent: Better Auth's endpoints for verifying an email, resetting a password, or changing an email answer `404`. An address gets at most one code a minute for each place a code signs in, the installation or a learn domain (access-32), whoever asks and however many ask at once, and spending a code's guesses does not reset the minute. Asked for again while it still signs in, the same code is sent, its ten minutes renewed and its guesses kept, so a late mail is never stale; spent, expired, or out of guesses, a new one replaces it. In production, Better Auth's limiter admits 120 code requests and 120 sign-in attempts per `X-Forwarded-For` value, counted apart, so a class behind one address can sign in at once; each count restarts a minute after its last admitted request, and is kept per process, not coordinated across the installation (deployment guide). Each code's mail names the site it signs in at. `apps/server/auth/auth.test.ts`, `apps/server/persistence/sign-in-code.test.ts`, `apps/server/mail/sign-in-code.test.ts`
- **access-3:** Codes go out through the `sendMail` the host passes to `createServer`; the server's `serve` sends them over SMTP, or into its log while listening on loopback alone (`serve`'s wiring of either untested), and does not start without SMTP unless `BRAIVO_URL` is loopback ([ADR 0033](../adr/0033-email-over-smtp.md)). The request waits for `sendMail`: if that fails, it is refused `503` with `SIGN_IN_CODE_SEND_FAILED` rather than answered as sent, and `/login` stays at the email, saying so; the address still waits its minute, as a failure may follow a message the mail server accepted. `apps/server/server.test.ts`, `apps/server/config.test.ts`, `apps/server/auth/auth.test.ts`, `packages/auth-client/sign-in.test.tsx`
- **access-4:** A code is asked for and redeemed, a password signs in (access-1), and Google's sign-in started (access-30), only as JSON on the installation's host, with its own `Origin` if one is sent (access-28): Better Auth checks the origin only of a request carrying a cookie, so otherwise another site could sign a visitor in to an account whose code it holds, or start Google's sign-in in their browser. `apps/server/api/app.test.ts`, `apps/server/api/google.test.ts`, `apps/server/api/reviewer.test.ts`
- **access-5:** The console's `/login` asks for an email, saying that using the code sent there creates the account if there is none, then the code sent to it, which its last digit, typed or pasted (spaces and dashes in a paste dropped), submits (only Sign in resends it unchanged), then, for an account without a name, a name, each step under its own heading; "Send the code again" waits out the server's minute from each send, or from a resend refused for it or failed, counting it down, and a code expired or out of guesses can no longer be typed, its main button, "Send a new code", sending a new one; an email refused for its minute (asked again after Back, a reload, or in another tab) goes on to the code already sent, saying so, unless its last send here failed; a name of spaces alone is refused before it is sent. A request unanswered within 10 seconds, sending or checking a code, naming the account, or starting Google's sign-in, is given up: the step stays, what was typed included, and says it could not connect, to try again; but a code asked for, which the server may still send, goes on to the code (or stays there), saying it could not confirm one was sent and to send it again, at once, if none arrives, the code step saying to enter one if it arrives rather than that one was sent. Naming an account whose session has ended goes back to the email, saying so. The page names Braivo's console, tells a learner who landed there to sign in from their course's website, and on a wide screen says what Braivo does; a learn domain's sign-in (access-13) shows none of it. With `BRAIVO_PRIVACY_URL` and `BRAIVO_TERMS_URL` set (both or neither, as `GET /api/sign-in-settings` says; unread within its 3 seconds, as unset), the email step, a learn domain's sign-in's too, says continuing agrees to those pages, each opening in a new tab. After sign-in it goes, in `/login`'s place in the history, to the `redirect` search parameter if that stays within the origin, else `/`; an account with a name that opens it signed in goes there at once. `packages/auth-client/sign-in.test.tsx`, `packages/ui/ui.test.tsx`, `packages/auth-client/redirect.test.ts`, `apps/console/test/sign-in.test.tsx`, `apps/server/config.test.ts`, `apps/server/server.test.ts`
- **access-30:** An installation with Google's OAuth client (`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, both or neither) offers "Continue with Google" at the email step of `/login`, a learn domain's included, as `GET /api/sign-in-settings` says; `/login` asks with a 3-second deadline, and one that cannot ask, or gets no answer by then, offers codes alone. Google asks the person to choose an account each time, by redirect only (no ID token is accepted, nothing links an account by hand), and returns to the `redirect`, or for a learn domain, whose own "Continue with Google" leaves through a handoff (access-12), to the installation's `/login?handoff=`, which offers the account as access-13 says. Only an email Google has verified, and only while it is still the account's, makes an account, signs in to the one that email's code made, or signs in again; otherwise nothing is signed in and `/login` says which. Any other failure, a cancel included (Google reports it as it does an administrator's block), offers to try again or use a code; one whose saved state is gone returns to the console's own `/login`. Google's access and refresh tokens are kept encrypted. `apps/server/api/google.test.ts`, `apps/server/config.test.ts`, `apps/server/server.test.ts`, `packages/auth-client/sign-in.test.tsx`, `apps/console/test/sign-in.test.tsx`
- **access-36:** The console's settings are at `/<organization>/settings/<page>`; `/<organization>/settings` opens at `account`, and a page they do not have, such as `billing`, says so among them. They replace the console's sidebar with their own navigation, down the side, or on a phone one row scrolling sideways to the page shown. It leads back to the page in that tab they were opened from if it is the organization's, else to its home; so does Escape, unless an open dialog or menu takes it to close, or the focus is in a field typed in or a select. The organization's pages (General, Members, Groups, Domains) are offered to an `owner` or `admin` alone; to a teacher or an `author` each says there is no such setting, reading nothing (access-39, access-43). The account menu opens them on an organization's pages, focusing the page shown in their navigation; leaving them focuses the menu again, or on a phone what opens the drawer holding it. `/settings/account` shows the account's email, which cannot be changed (access-2), and renames the account everywhere, not only in that organization, through Better Auth's `update-user`: trimmed, a name of spaces alone refused before it is sent; a refusal, or no answer within 10 seconds, keeps the name typed and says it could not be saved, a new alert each time; a session ended meanwhile goes to sign in, and back. `apps/console/test/settings.test.tsx`, `apps/console/lib/app-page.test.ts`
- **access-37:** An organization's `owner` or `admin` renames it with `POST /api/organizations/:organizationId/rename` `{ name }`, trimmed and checked as setup's (access-31), else 400 `NAME_INVALID`; a member who only studies there, or an organization deleted meanwhile, 403. Its learn domain names it so from its next load (white-label-6). The console's `/<organization>/settings/general` shows the name, editable, and the console address, which cannot be changed yet (ADR 0004). Saved, every page names the organization so; refused or unanswered within 10 seconds, the name typed stays and an alert says why, a new one each time; a session ended meanwhile goes to sign in, and back; an organization no longer theirs reads as not found. Another organization's page starts from its own name, nothing typed carried over. Below the name, a switch lets tools read the organization's learners' data (access-45), saying that tools its members connect, such as the `braivo` CLI, can then read learners' names, progress, and learning history, which an AI app receiving it may send to its provider, and that turning it off stops further reads but cannot recall what a tool already received; turning it on asks first in a dialog restating that, cancelling leaving it off; turning it off applies at once. Under it, who last changed it and when ("Turned on by Ana Kowalska on October 30, 2026"), the date alone once that account is gone, nothing before the first change. The page reads the setting itself, within 10 seconds, never from the organizations listed to every member; while it loads or once that read fails, no switch shows, the failure said; saved, it shows the answer, and from the first save on no later read until reloaded, since one may have begun before it; pending, a failure, and a session ended meanwhile as the name's save, the switch staying as it was, except that unanswered or failed in the server, the alert says the change may have been saved and to reload to check. Another organization's page reads its own. `apps/server/application/organizations.test.ts`, `apps/server/api/tools-read-learner-data.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/api/policy.test.ts`, `apps/console/test/settings.test.tsx`
- **access-6:** Each app's signed-in pages check the session before showing anything, fetching nothing else first, and again on each navigation (untested): a signed-out visitor, or an account without a name, goes to `/login?redirect=<href>`, starting at the name step for the latter, so no account without a name reaches a signed-in page. A session that cannot be checked, within 10 seconds or at all, signs no one out: the page says something went wrong and offers Try again. A failed Sign out, one unanswered within 10 seconds included, keeps the page and says it could not sign out; clicking again retries. `packages/auth-client/require-session.test.ts`, `apps/console/test/sign-in.test.tsx`, `apps/console/test/connect.test.tsx`, `apps/learn/test/sign-in.test.tsx`
- **access-7:** Every `/api` answer, on any host, refusals and 404s included, carries `Cache-Control: private, no-store`, Better Auth's under `/api/auth/*` too. On `BRAIVO_URL`'s host, a POST under `/api/auth/*` with a body over 1 MB answers `413`. `apps/server/api/app.test.ts`, `apps/server/api/policy.test.ts`
- **access-8:** On any host but `BRAIVO_URL`'s, the server answers `401` to a request carrying `Authorization`, whatever it carries, a valid bearer token included; without one, Better Auth (`/api/auth/*`), the handoff's installation end (`/api/handoffs*`), and the console's `/api/organizations*` and `/api/organization-setup` answer `404`: an organization's domain serves its learn app and nothing else, its sign-in included, which asks `/api/sign-in-settings` there too ([ADR 0004](../adr/0004-one-application-origin.md)). `apps/server/api/app.test.ts`, `apps/server/api/policy.test.ts`

### Content owners' tools

- **access-9:** A content owner's `braivo` CLI gets a session token through the device flow and sends it as `Authorization: Bearer`, acting as the person who approved it, with that person's roles and no more ([ADR 0022](../adr/0022-machine-access.md)). Braivo answers only its own client, and a token it never issued opens nothing. `apps/server/api/app.test.ts`
- **access-10:** Of `/api/auth/*`, a token reaches `get-session` and `sign-out` alone, the latter ending its own session only (`braivo logout`); anything else answers `403`. No answer to a token sets a cookie, its session's renewal included; an account's cookie session, by contrast, is renewed through both Braivo's own routes and Better Auth's (the latter untested). `apps/server/api/app.test.ts`, `apps/server/api/materials.test.ts`
- **access-11:** The console's `/device` names the tool and the code, and lets the person signed in approve or deny the tool's request, one decision at a time. It calls a code invalid or expired only when Better Auth refuses it, and on any other failure offers to try again; a code already answered offers nothing to approve. The decision being sent names itself on its button ("Approving…"); unanswered within 10 seconds, it is given up, offered again. Refused, it reads the code again: one an earlier, given-up try answered after all shows that outcome, focused like any other. Someone signed out, before or meanwhile, returns to the code once signed in. `apps/console/test/connect.test.tsx`
- **access-40:** An AI app connects at `<BRAIVO_URL>/mcp` by OAuth, as a grant to one app for one organization ([ADR 0045](../adr/0045-remote-mcp.md)). Every authorization first asks, at the console's `/consent`, which organization the person may author in (`owner`, `admin`, or `author`, [ADR 0048](../adr/0048-author-role.md)) it works in, listing those alone; someone authoring in none is told so and may cancel, which sends the app back `access_denied`, granting nothing. The choice is kept on their session and checked again at consent: one they only learn or teach in is refused (`403`), granting nothing, as is resuming or consenting for an organization other than the one the page showed, chosen since in another tab, whose refusal alone carries `code: "ACTIVE_ORGANIZATION_CHANGED"`: the console says so for it, and for any other refusal that it could not connect the app, to check access and start again. Since every authorization asks, one with `prompt=none` answers `interaction_required`. Then `/consent` names the app and that organization, and the app's client ID when that is a URL (its name being the app's own claim), unless that person consented to that app for it already. Each answer the page sends names itself on its button while sent ("Approving…", the organization chosen marked busy); each request it makes, unanswered within 10 seconds, is given up, to try again. A session ended meanwhile is answered `401`, not as another tab's choice; the console sends them to sign in, then back to choosing the organization, since a new session has none chosen. The grant, its codes, refresh tokens, and access tokens (claim `organization_id`) are for that organization alone, so grants of one person and app for two organizations are independent. Its one scope is `braivo:author`, which the protected resource metadata advertises. `apps/server/api/mcp.test.ts`, `apps/console/test/connect.test.tsx`
- **access-41:** Each request to `/mcp` is refused `401` `invalid_token` once its grant is disconnected (access-42), though its token still verifies, and so is a token issued before the grant was given again (to the second); `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="braivo:author"` without that scope, before any tool runs. Its tools call Braivo's routes in-process as the connection, with its person's roles read per call, and reach only those `braivo:author` grants: the organization's sources, objectives, and citations, creating courses and writing and retiring tasks, as a token does (ADR 0039: what it writes waits unpublished, and retiring a published task is refused), and reading its courses and tasks, never publishing, deleting a course, groups, members, progress, or settings (`403`); a route naming another organization answers `403`; `GET /api/organizations` answers the grant's organization alone, while its person authors in it; what a route names beside the organization is checked as for any credential (access-24). `apps/server/api/mcp.test.ts`, `apps/server/api/principal.test.ts`
- **access-42:** A person sees and ends their own connections, never another's. `GET /api/connections` lists each grant they gave, one per app and organization, oldest first: its app's registered name and client ID, the organization, and when it was given. `POST /api/connections/:id/disconnect`, a trusted write (access-28), deletes that grant's consent and every refresh token of that person, app, and organization, in one transaction, so the app's next `/mcp` call is refused (access-41) and its refresh refused `invalid_grant`. A refresh token is honoured only while a consent of its person, app, and organization stands, given by the token's creation at the latest (whole seconds): one a rotation inserts after the disconnect, or one from before the grant was given again, mints nothing, except one issued in the second it is given again. So that Braivo reads a token request as Better Auth does, one that is not `application/x-www-form-urlencoded`, or sends `grant_type` or `refresh_token` twice, is refused `400` `invalid_request`. Their grant to that app for another organization, and another person's to it, keep working. `404` for an ID not theirs. Both take the browser's session alone: a device-flow token or a connection is refused `403` (ADR 0022). The console's `/<organization>/settings/connections`, "Connected apps" among the account's settings, lists them, the app by name with its client ID when that is a URL, then the organization and the date; Disconnect asks first, then removes the row and says so, without reading the list again. To someone authoring in an organization, as consent offers only those (access-40), it also says how to connect one, with the address, `<BRAIVO_URL>/mcp`, to copy and a link to the guide. `apps/server/api/mcp.test.ts`, `apps/console/test/settings.test.tsx`
- **access-45:** An organization lets tools read its learners' data, or not: off by default, for every organization ([ADR 0050](../adr/0050-tools-read-learner-data.md)). A request is a tool's when it comes with a device-flow token or as a connection, and a browser's otherwise; one carrying `Authorization` is a tool's whatever cookie it also carries, and acts as the token's person, never the cookie's. While off, a tool is refused, whatever its person's roles: a course's overview and another member's report, as a missing course is (`404`, progress-1, progress-12); and the member list (access-26), the groups (access-38, access-39), even those its person teaches, and changing a group, whose answer lists its people, `403`, the refusal those routes already give. A change is refused before anything reads the organization's people or groups or is written, so a tool learns nothing from a `400` for a non-member or a `404` for a missing group; what is wrong with a change by itself (a malformed body, a blank name, an ID twice, one person in both roles, nothing named) is still `400`. Creating a group, which answers only its ID, and recording evidence stay open to tools. The console, in a browser, reads either way, as does anything driving a signed-in browser, which presents its session (ADR 0050), and a learner's own report stays readable through any tool, under every other check. On, a tool reads and changes what its person may, no more. The setting of the organization owning the course, or named by the members' or groups' route, is read on each of these requests a tool makes, so one admin's token reads and changes where it is on and is refused where it is off, and switching it off refuses the token's next request. An `owner` or `admin` reads and sets it, from a browser alone, with `GET` and `POST /api/organizations/:organizationId/tools-read-learner-data` `{ allowed }`, answering `{ allowed, changedBy: { userId, name } | null, changedAt }` (access-37); anyone else `403`, and any tool `403` explained, even an owner's token or a cookie beside one, so no tool grants itself access or reads who decided, and no connection reaches either (access-41). A change records who made it and when, only if it changes the value: setting the value it has keeps the record, so two turning it on at once record one change; otherwise the last one's word is final. The account deleted, the value and the time stay, `changedBy` `null`. Better Auth's organization update cannot change any of it, and none of it is in its answers. `apps/server/application/organizations.test.ts`, `apps/server/api/tools-read-learner-data.test.ts`, `apps/server/application/access.test.ts`, `apps/server/application/course-progress.test.ts`, `apps/server/application/learner-progress.test.ts`, `apps/server/application/groups.test.ts`, `apps/server/api/learning.test.ts`, `apps/server/api/groups.test.ts`, `apps/server/auth/auth.test.ts`

### Learn domains: sign-in and learner session

An organization's domain never holds the account's session or takes its credentials: it holds a learner session, Braivo's own ([ADR 0018](../adr/0018-sign-in-and-invitations.md)), opened there by a code good there alone, or, for Google, whose callback is the installation's, handed over from the installation's origin. The handoff is OAuth's authorization code flow in miniature: the domain starts it, the installation's console completes it, and the domain redeems it.

- **access-32:** On a host serving an organization, `POST /api/session/code` `{ email }`, a trusted write (access-28), emails any valid address a code that signs in on that hostname alone, for the organization it serves when sent, in the language `Accept-Language` prefers (localization-6), saying nothing of whether the address has an account or is a member: `204`. A code has access-1's rules, its own minute between codes (access-2) refused `429` `SIGN_IN_CODE_COOLDOWN`, and a failed send `503` `SIGN_IN_CODE_SEND_FAILED`; asked for again, it is the same code while it still signs in there for the same organization (access-2). It is stored as a random seed, the code being an HMAC of it under the installation's secret, bound to the hostname and address, never as a plain hash, and expired codes are deleted as new ones are sent. Each client, as Better Auth's limiter tells clients apart (`X-Forwarded-For`, an IPv6 address by its /64), gets 120 code requests and, apart, 120 sign-in attempts in each minute, refused `429` past them; kept per process. On the installation's host, or a host serving no organization, `404`. `apps/server/api/learner-sign-in.test.ts`, `apps/server/api/client.contract.test.ts`
- **access-33:** `POST /api/session/sign-in` `{ email, code }` there, a trusted write, checks the code: `400` without a code of six digits, counting no guess; `400` `INVALID_OTP`, counting a guess, `400` `OTP_EXPIRED` for none, an expired, or a spent one, and `403` `TOO_MANY_ATTEMPTS` from the fifth wrong guess, after which the right one is refused too, guesses at once each counted. A right code makes the address's account if there is none, verified and unnamed, as Better Auth's code sign-in does, one account however many sign in with it at once; for an account not a member of the organization it is refused `403` `NOT_A_MEMBER`, spending nothing, so the same code signs in once the operator adds it (access-21). For a member it is spent only if, when spent, it is still unexpired, not guessed out meanwhile, and the hostname still serves the organization it was sent for; then `__Host-braivo-learner` is set as access-15's, and the answer is who is signed in. A learn domain's code opens no account session, and the installation's codes open no learner session. `apps/server/api/learner-sign-in.test.ts`, `apps/server/api/client.contract.test.ts`
- **access-34:** `POST /api/session/name` `{ name }` there, with that learner session, names its account only while it has none: trimmed, 1 to 200 characters, else `400` `NAME_INVALID`; `204`, or `409` `ALREADY_NAMED` once it has one, which the learn app takes as named and goes on. `apps/server/api/learner-sign-in.test.ts`, `apps/learn/test/sign-in.test.tsx`
- **access-35:** The learn app's `/login`, on a host serving an organization, is its sign-in form, under the organization's name ("Sign in to Fernwood", the tab "Sign in · Fernwood"), never Braivo's, by access-32 to -34: the email, the code, then a name for an account without one, as the console's form (access-5), but its email step says to use the address the organization knows them by, never that signing in creates the account: a code makes one (access-33), yet only the operator admits it (access-21); `NOT_A_MEMBER` says to ask to be added with that email, then sign in again while the code lasts. Signed in there already, it goes on to `redirect`; signed in unnamed, it starts at the name. It waits at most 10 seconds for the reads deciding how to sign in, the host's organization and the session, then fails, offering Try again; for what it offers besides the code, at most 3 seconds, then offers the code alone. Google is offered as access-30 says. `apps/learn/test/sign-in.test.tsx`

- **access-12:** The learn app's "Continue with Google" leaves through the domain's `GET /api/session/sign-in?redirect=<path>&provider=google`. That records a handoff for the organization and hostname the request's host serves, for 15 minutes, with the path if it stays on the domain, else `/`; sets its nonce in the `__Host-braivo-handoff` cookie; and redirects to `BRAIVO_URL/login?handoff=<id>`, with `&provider=google` when asked so. Once another handoff is begun in the same browser on the same domain, an earlier one not yet finished can no longer finish. `apps/learn/test/sign-in.test.tsx`, `apps/server/api/session.test.ts`, `apps/server/application/learner-sessions.test.ts`
- **access-13:** At `BRAIVO_URL/login?handoff=<id>`, the console names the organization and the domain, in the tab's title too, never Braivo. A handoff it cannot read within 10 seconds fails the page, offering Try again. An account already signed in is offered, never used unasked: "Continue as <name>" (its email while it has none, to be named first), or "Use another account", which signs the current account out (unconfirmed within 10 seconds, it keeps the account offered and says it could not sign out); otherwise it signs in by code, name step included, as it does when the session cannot be read within 10 seconds. With `provider=google` and no account open, it starts Google at once, coming back without `provider`, and offers the form if Google cannot be started. A session found ended meanwhile goes back to signing in. `apps/console/test/sign-in.test.tsx`
- **access-14:** Continuing is a trusted write (access-28) from a click, never a navigation, so no link hands a signed-in visitor over unasked: `POST /api/handoffs/:id` checks the account is a member of the organization, then issues a code that expires with the handoff, within 60 seconds; issuing again replaces the code without extending the handoff. The page then navigates to `https://<hostname>/api/session/handoff?code=…`; unanswered within 10 seconds, it offers continuing again, safe since the code is replaced. An account that is not a member is told to ask the organization to add it by its email, named when the session can still be read, and may try again while the handoff lasts, or use another account. A handoff no longer available reads as expired, without Braivo's name; when it expires mid-sign-in, the page links to `https://<hostname>/login`, where the domain, while it serves the organization, starts another. `apps/server/application/learner-sessions.test.ts`, `apps/server/api/session.test.ts`, `apps/console/test/sign-in.test.tsx`
- **access-15:** The domain redeems the code once, only with the nonce cookie, on the hostname the handoff began on, before it expires, and while that hostname still serves its organization. It sets `__Host-braivo-learner`, lasting a week and renewed by use once a day old, and redirects to the stored path with `Referrer-Policy: no-referrer`. Anything else spends nothing and redirects to `/login?failed=1`, where the learn app, unless the learner is signed in already, shows its form saying Google's sign-in did not work, offering it again on a click only, so a handoff failing every time (cookies blocked) cannot cycle unseen. `apps/server/application/learner-sessions.test.ts`, `apps/server/api/session.test.ts`, `apps/learn/test/sign-in.test.tsx`
- **access-16:** A handoff's nonce and code, and a learner session's token, are 256 bits, random (untested), and stored only as their SHA-256, which redeems nothing itself. The `__Host-braivo-handoff` and `__Host-braivo-learner` cookies are `Secure`, `HttpOnly`, `SameSite=Lax`, on that host alone. Expired learner sessions are deleted as new ones are written, and expired handoffs likewise. `apps/server/api/session.test.ts`, `apps/server/application/learner-sessions.test.ts`
- **access-17:** A learner session fixes a user, an organization, and the domain it was handed to, and grants nothing by itself: it is read only on that domain while it still serves that organization, so a token kept by a domain's former operator opens nothing on the organization's next domain, and authorizes only the learner routes, `GET /api/courses`, a course's `…/next`, `…/activity`, and `…/attempts`, and the learner's own progress report; those routes recheck membership on every request. Who is signed in, and signing out, are access-18. An account's cookie on a learn domain counts for nothing. `apps/server/api/learning.test.ts`, `apps/server/application/learner-sessions.test.ts`
- **access-18:** `GET /api/session` answers who is signed in on the host asked, and `POST /api/session/sign-out` ends that host's session: on a learn domain its learner session alone, on the installation's host the account's, signed in or not. The learn app's sign-out returns to sign-in. `apps/server/api/session.test.ts`, `apps/learn/test/sign-in.test.tsx`
- **access-19:** On the installation's host, which serves the learn app only in development, learner routes take the account's session, and the learn app's `/login` signs in by code there. `apps/server/api/learning.test.ts`, `apps/learn/test/sign-in.test.tsx`

### Organizations, members, and roles

- **access-20:** The operator creates an organization: the server's `organization create --name --slug --owner <email>` makes it, for an account that has already signed in, its `owner`. Better Auth's creation endpoint creates none, and an HTTP request cannot create one by naming a `userId` in place of a session. `apps/server/auth/auth.test.ts`
- **access-31:** On an installation with `BRAIVO_SELF_SERVE_DOMAIN`, a session whose account owns no organization sets one up, its `owner`, at `POST /api/organization-setup` `{ name, slug }`, a JSON write: 201 with the organization as `GET /api/organizations` lists it, its learn domain `<slug>.<that domain>` registered. Refused, creating nothing: `400` a name blank, over 100 characters, or holding NUL, a slug the slug rules refuse, or a reserved service name (`www`, `admin`, `domains`, and the others `apps/server/application/organizations.ts` lists), saying whether it is malformed or reserved; `409` an account already owning one, or a slug or hostname taken; each saying which in English and in a code for a client to word (`NAME_INVALID`, `ADDRESS_INVALID`, `ADDRESS_RESERVED`, `ADDRESS_TAKEN`, `ALREADY_OWNER`). A failure once it is created, registering the domain included, deletes it again, so a retry starts clean, unless the database fails that too. Of one account's setups made at once, at most one stays. Without the setting it answers `404`; `GET /api/organization-setup` answers `{ "domain", "maySetUp", "dataRegion", "otherRegions" }`: `domain` `null` there; `maySetUp` whether the account owns none, `false` there; `dataRegion` the code `BRAIVO_DATA_REGION` sets (`EU`), else `null`; `otherRegions` those `BRAIVO_OTHER_REGIONS` lists, each `{ "region", "setupUrl" }`, `setupUrl` `null` while not yet open (ADR 0040). The console's `/join` offers the setup to whoever may: someone managing none lands there, and an `admin` elsewhere owning none reaches it from the sidebar's organization menu, "Set up an organization", shown even beside their one organization; an owner is sent to their organization. It asks the name and shows the address it makes, editable, which opens itself when the name makes none or Braivo refuses the address; created, it opens the new organization's page. Unanswered within 10 seconds, as on a server error, it may have been created: the page says so, to reload before trying again. Where the installation says its region, the data region comes first: a select, its own chosen, if other regions are listed, else shown as fact. Another open region replaces the form, kept as typed, with a link, "Go to the <region> site", to that installation's `/join`, creating nothing here; one not yet open is listed, disabled. To someone managing none, it still says to open their school's site if learning, and names the signed-in email for whoever adds a member. With the setting, the server refuses to start with an AI key unless `BRAIVO_AI_ORGANIZATIONS` lists who may spend it. `apps/server/api/organization-setup.test.ts`, `apps/server/application/organizations.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/config.test.ts`, `apps/console/test/organizations.test.tsx`
- **access-21:** Until invitations, only the operator adds members: the server's `organization add-member --slug --email [--role member|author|admin]` adds an account that has already signed in, as `member` (the default, untested: a learner), `author`, or `admin`, one role, never `owner`, and refuses one that is already a member rather than giving it another role, or one past an organization's 1,000 members, staff included. Nothing over HTTP adds a member (untested; invitations are access-27). The learner, once added, signs in on the organization's learn domain. `apps/server/auth/auth.test.ts`, `apps/server/cli/index.test.ts`
- **access-22:** An organization that still owns objectives, courses, sources, or files is not deleted (`409`; courses, sources, and files untested), and a refused delete keeps its members; one that owns none of those is deleted. Its slug follows white-label-8 ([white-label](white-label.md)). `apps/server/auth/auth.test.ts`
- **access-23:** A user has at most one member record per organization, carrying one or more organization roles. Roles are checked one by one, never compared whole: a `member` who also holds `admin` administers. Membership is enrollment: a member in any role reaches every course of its organization, whatever groups they are in ([learner loop](learner-loop.md), learner-loop-2 and 3). `apps/server/persistence/membership.test.ts`, `apps/server/application/permission.test.ts`
- **access-24:** A request naming an organization authorizes nothing: on every route that acts on a named organization and reads or writes anything, the actor is the session's user and their role there is checked (an empty evidence batch does neither): it answers `401` without a session, and `403` to a session without the role there. Roles grant what the table says; a `member` never authors or records evidence, and an `author` authors but never records evidence or reaches people (access-43). `apps/server/api/authoring.test.ts`, `apps/server/api/policy.test.ts`, `apps/server/application/objectives.test.ts`, `apps/server/application/tasks.test.ts`, `apps/server/application/courses.test.ts`, `apps/server/application/record-evidence.test.ts`, `apps/server/auth/auth.test.ts`

| Ability                                                         | `owner`   | `admin`        | `author`                               | `member`                               |
| --------------------------------------------------------------- | --------- | -------------- | -------------------------------------- | -------------------------------------- |
| List and study the organization's courses                       | yes       | yes            | yes                                    | yes                                    |
| Author sources, objectives, tasks, courses; publish (access-43) | yes       | yes            | yes                                    | no                                     |
| Record evidence                                                 | yes       | yes            | no                                     | no                                     |
| Read a learner's progress                                       | yes       | yes            | own, and those they teach (progress-1) | own, and those they teach (progress-1) |
| Read a course's overview of every member (progress-12)          | yes       | yes            | no                                     | no                                     |
| Define and change groups (access-38)                            | yes       | yes            | no                                     | no                                     |
| List groups (access-38, access-39)                              | every one | every one      | those they teach                       | those they teach                       |
| Appear in `GET /api/organizations` and the console              | yes       | yes            | yes                                    | if they teach a group (access-25)      |
| List the organization's members                                 | yes       | yes            | no                                     | no                                     |
| Rename the organization                                         | yes       | yes (untested) | no                                     | no (untested)                          |
| Delete the organization                                         | yes       | no (untested)  | no                                     | no (untested)                          |
| Create an organization                                          | no        | no             | no                                     | no                                     |

A member of any role who teaches a group also reads its learners' progress, and its courses' overviews of them (access-39): a group grants that, not a role. Roles add up: `author` beside `member` is `author`, beside `admin` adds nothing, and taking it from someone with no other role leaves them a `member`. Renaming is access-37, by an `owner` or `admin`; deleting is Better Auth's default access control, which gives `author` no permission; an owner's rename and delete through Better Auth are tested. Creating one is no role's: the operator's (access-20), or with self-serve, anyone's who owns none (access-31).

- **access-25:** `GET /api/organizations` answers the organizations the session's user administers, authors in, or teaches a group in, an empty group included, by name, each with `administers` (whether they hold `owner` or `admin` there), `authors` (`owner`, `admin`, or `author`), `teaches` (a teacher of one of its groups), and `learnDomain`, the hostname its learners practise on, the latest registered of its learn domains (white-label-1), or `null` before one is, only to a session, never cached; the console resolves `/<slug>` among them (white-label-7). An organization's page, and each of its courses' (a course is open to every learner once created), says where its learners practise, with a way to copy the address, or that they have nowhere yet. `apps/server/api/authoring.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/server/mcp/server.test.ts`, `apps/console/test/shell.test.tsx`
- **access-26:** Only an `owner` or `admin` lists an organization's members, at `GET /api/organizations/:organizationId/members` or in a course's overview (progress-11), through a tool only as access-45 allows: user IDs, names, and every role, with no cap (untested; listing past 100 is tested), and never emails. A teacher's overview shows only the learners they teach, without roles (access-39). Better Auth's `list-members`, `get-full-organization`, `get-active-member-role`, `remove-member`, and `update-member-role` answer `404`, even to an owner; removing a member or changing a role takes the database. The console's `/<organization>/settings/members` lists them read-only, by name, each role as a school says it (`member` as Learner, `author` as Author) with the groups they teach (access-38), the account's own marked, and says they cannot be added or removed there yet, but whoever runs Braivo for it can. `apps/server/api/authoring.test.ts`, `apps/server/api/learning.test.ts`, `apps/server/auth/auth.test.ts`, `apps/server/persistence/membership.test.ts`, `apps/console/test/settings.test.tsx`
- **access-27:** Better Auth's invitations are off: its invitation endpoints answer `404` on every host, even to requests they would carry out, and a stored invitation stays pending and admits no one. `apps/server/auth/auth.test.ts`

### Groups and teaching

- **access-38:** An `owner` or `admin` defines the organization's groups ([ADR 0042](../adr/0042-groups-scope-teaching.md)): `POST /api/organizations/:organizationId/groups` creates one whole, its name, learners, teachers, and courses, idempotently by an optional `key` compared with the creation; `POST …/groups/:groupId` changes one by what it names, answering it as it then stands: a new name, people and courses removed, then people added in a role and courses added. Adding what is there or removing what is not does nothing, and concurrent changes apply in turn, the last one's word final. A role changes only when one change removes and adds the person; adding someone already there in the other role answers `409`. `GET …/groups` lists them all. A tool lists and changes them only as access-45 allows; it creates them either way. Each person is a member of the organization, in one role, `learner` or `teacher`, and each course the organization's; an ID twice, one person in both roles, a non-member, another organization's course, or a change naming nothing answers `400` saying which, and a field the route does not know a bare `400`. Leaving the organization leaves its groups; deleting a course removes it from them; neither touches evidence. No route deletes a group. The console's `/<organization>/settings/groups` lists the groups by name, counted, found by name; `/settings/groups/new` and `/settings/groups/<group>` set a name and pick teachers, learners, and courses among the organization's, saying whose progress the teachers will read. Creating sends the whole group under one key per visit to the form; after an unconfirmed answer the form holds what it sent, so trying again sends the same group, never creating two, and a creation answered after its page was left moves nobody back to it. Changing sends only what the form changed over the group as loaded, nothing when nothing did, a role changed by removing and adding the person; a change undone before saving is dropped, so reloading the group never turns it into a new one. A `409` reloads the group, showing whom someone else put in the other role meanwhile, as they now are, and leaving that addition out; the form's other changes stay, as they do when a reload fails. An unconfirmed change is never resent by itself, nor saved again until the group is reloaded, its alert staying until then; a name another member shares is told apart by the end of their user ID, wherever a learner is chosen or named; leaving with changes unsaved asks first. `apps/server/application/groups.test.ts`, `apps/server/api/groups.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/console/test/groups.test.tsx`, `apps/console/lib/group-edits.test.ts`
- **access-39:** Teaching a group grants reading, for each course it takes, its learners' progress and the course's overview of them (progress-1, 11, 12), and nothing else: no authoring, evidence, member list, defining or changing groups, or other course. `GET /api/organizations/:organizationId/groups` answers any other member the groups they teach there, with their learners and courses, none if they teach none, and a non-member `403`; to a tool, only as access-45 allows. Membership still decides who studies a course: a group scopes teaching, not practice. In the console the organization of a teacher who does not author opens at `/<organization>/groups`, its sidebar's one section: each group they teach, its teachers, its learners counted and listed on request, and its courses, each leading to the course's progress (progress-11) of every group they teach it to, said so. Its courses, sources, and organization settings are refused them before anything is read; an administrator's Groups page shows every group, each with a way to edit it. `apps/server/application/groups.test.ts`, `apps/server/api/groups.test.ts`, `apps/server/api/client.contract.test.ts`, `apps/console/test/groups.test.tsx`
- **access-43:** An `author` ([ADR 0048](../adr/0048-author-role.md)) manages all of the organization's content as an `owner` or `admin` does — sources and files, reading and drafting with Braivo's AI (generation-8), objectives, citations, tasks, courses, publishing, hiding, retiring, and deleting what may be deleted — every author all of it, whoever wrote it, and through tools only what any tool may ([authoring](authoring.md), Who). It reaches no person's data: listing members, groups beyond those they teach, defining or changing groups or which courses they take, every member's course overview or a learner's progress they do not teach (`404`, as for any member), recording evidence, renaming, domains, and Better Auth's organization update and delete, and its member, role, and invitation routes, are refused it, as to any `member`; it studies the courses and answers its own tasks as any member. Roles are read on every request, so a session, token, or connection authors nothing once the role is taken. In the console, an author's organization opens at Courses, its sidebar Courses and Sources, and Groups if they teach (otherwise `/<organization>/groups` says they teach none, reading nothing); a course's page links to every member's progress only for an administrator; the organization's settings are refused before anything is read (access-36). `apps/server/api/roles.test.ts`, `apps/server/application/permission.test.ts`, `apps/server/auth/auth.test.ts`, `apps/server/api/mcp.test.ts`, `apps/console/test/groups.test.tsx`, `apps/console/test/connect.test.tsx`

### Write origins

- **access-28:** Braivo's own writes, except an upload, whose check sources-11 owns ([sources](sources.md)), are refused `403`, recording nothing, with or without a session, unless their media type is `application/json` and their `Origin`, if sent, is the host's own: `BRAIVO_URL`'s on the installation's host, and on a hostname currently serving an organization, that hostname's HTTPS origin on the default port. A learn domain cannot write through the console's session. `apps/server/api/authoring.test.ts`, `apps/server/api/pdf-to-tutor.test.ts`, `apps/server/api/policy.test.ts`, `apps/server/auth/origin.test.ts`
- **access-29:** Better Auth checks the `Origin` of a request carrying a cookie, trusting `BRAIVO_URL`'s origin alone, never an organization's domain: such a write from a foreign origin is refused. Better Auth does not check the `Origin` of a request without a cookie, which is why sign-in codes pass access-28 too (access-4). `apps/server/auth/auth.test.ts`

### Framing and scripts

- **access-44:** No site may frame the console or a learn app, so no page can hijack a click such as continuing a handoff (access-14), and either runs scripts from its own origin alone: each app's `public/_headers`, copied into its build, sends `Content-Security-Policy` with `frame-ancestors 'none'` and `script-src 'self'`, beside `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, applied by whatever serves the build ([deployment](../guides/deployment.md), The apps). Neither `index.html` runs an inline script: what must run before the first paint or the first render is a same-origin file, the console's `public/head.js` and `@braivo/i18n/boot`'s emitted script. Styles may be inline, as popovers are positioned through `style` attributes and the loading message's language is picked by a `<style>`. Whether a host applies the file is untested. `tooling/app-headers.test.ts`, `apps/console/styles.test.ts`, `packages/i18n/boot.test.ts`

## Boundaries

- Which hostname serves which organization, and the course routes' host ceiling: [white-label](white-label.md), white-label-4. The ceiling grants nothing by itself; this spec decides what a person reaches within it.
- What a learner's routes answer, a course outside their organizations included (learner-loop-3): [learner loop](learner-loop.md); who reads a report or an overview: [progress](progress.md), progress-1 and 12.
- Identity reaches use cases as plain user IDs, resolved by the route, with the access kind where a use case reads others' data (access-45): [architecture](../architecture.md).
- The language sign-in is in, and how its refusals are worded: [localization](localization.md).
- Not here yet: ADR 0018's invitations to an organization as `member` or `admin`, and a console UI for members, roles, and settings (see Gaps).

## Decisions

- [ADR 0004](../adr/0004-one-application-origin.md): one origin per app; the console addresses organizations by slug.
- [ADR 0005](../adr/0005-postgresql-drizzle.md): schema changes are committed migrations, generated from the schema.
- [ADR 0006](../adr/0006-better-auth.md): Better Auth owns identity and membership; organization context is not authorization; constraints its tables lack, like member uniqueness, come from Braivo's schema plugin.
- [ADR 0010](../adr/0010-hono-http-layer.md): a route resolves the session and passes user IDs to one use case.
- [ADR 0011](../adr/0011-ui-and-auth-client-packages.md): browser sign-in lives in `packages/auth-client`.
- [ADR 0016](../adr/0016-route-files.md): `_signed-in/route.tsx` guards signed-in pages.
- [ADR 0018](../adr/0018-sign-in-and-invitations.md): email-code and Google sign-in, invitations, learner sessions handed over to each learn domain; operator-created organizations.
- [ADR 0022](../adr/0022-machine-access.md): content owners' tools sign in by the device flow and act as them, on the installation's host only.
- [ADR 0033](../adr/0033-email-over-smtp.md): email over SMTP, or to the log of a loopback installation.
- [ADR 0042](../adr/0042-groups-scope-teaching.md): groups scope teaching; administration stays explicit.
- [ADR 0045](../adr/0045-remote-mcp.md): remote MCP at `/mcp`, a grant to one client for one organization.
- [ADR 0048](../adr/0048-author-role.md): an `author` manages and publishes content without administering the organization or reaching learners' data.
- [ADR 0049](../adr/0049-app-security-headers.md): each app's `_headers` is its policy; no inline script.
- [ADR 0050](../adr/0050-tools-read-learner-data.md): an organization decides whether tools read its learners' data, off by default.
