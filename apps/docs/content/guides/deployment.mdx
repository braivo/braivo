**There is no deployment packaging yet**: no image, no static serving, no supported proxy configuration. `bun run serve` serves the API and nothing else. Self-hosting is what Braivo is for, and this repository holds everything an installation runs, but building the apps and putting them in front of the API is yours to arrange until it is packaged.

```bash
bun run serve
curl -i http://localhost:3000/api/courses/<course-id>/next   # 401 without a session
```

The server mounts Better Auth at `/api/auth/*` and serves the learning API alongside it.

`bun --no-env-file apps/server/cli/index.ts config check` checks the environment `serve` reads without serving or reaching the database, so a release can stop on a bad one before replacing a running server; `bun run dev` runs it before starting anything. `bun --no-env-file apps/server/cli/index.ts db migrate` then applies the release's migrations; `bun run db:migrate` is for development, and loads the repository's defaults.

## Before you expose it

> [!WARNING]
> Do not expose the server directly. Put it behind a proxy that sets `X-Forwarded-For` itself and blocks direct access to the backend, and set `NODE_ENV=production`.

`NODE_ENV=production` enables Better Auth's rate limiting on its own endpoints. That limit is keyed on `X-Forwarded-For`, and the server does not give Better Auth the connection's address, so with nothing in front of it every caller shares one bucket per endpoint — 120 code requests and 120 sign-in attempts for the whole installation, each until a minute passes without an admitted one — and any caller can sidestep it by sending that header themselves. Braivo's own routes are not rate limited, but for a learn domain's sign-in (`/api/session/code` and `/api/session/sign-in`): 120 requests a minute to each per client, told apart as Better Auth's limiter does (its `X-Forwarded-For` value, an IPv6 address by its /64), in every environment, and none without the header; kept per process, so behind several processes each counts apart.

## The apps

Each app is served at the root of an origin that also serves `/api` from this server ([ADR 0004](https://github.com/braivo/braivo/blob/main/docs/adr/0004-one-application-origin.md)). `apps/console` goes on `BRAIVO_URL`'s origin; `apps/learn` goes on a domain serving one organization. A proxy in front must pass the `Host` header through unchanged. ADR 0004 is only partly implemented, so a procedure written today would describe a layout still changing.

Each build's `dist/_headers` is the app's security policy, in the format of Cloudflare's static assets: a Content-Security-Policy that lets no site frame the app and runs scripts from its own origin alone, `X-Content-Type-Options`, and `Referrer-Policy`. Have the static host or proxy serving `dist/` send those headers on every path, `index.html` served for an app's deep links included, and not serve the file itself; Cloudflare Workers and Pages apply it as it is to the files they serve, but not to a response a Worker or Pages Function makes, which must send the same headers itself. Cache for long only the files whose names change with their content (`assets/` holds them, Vite's and the boot script's); revalidate the rest, `index.html` and the console's `head.js` among them, which keep their names across releases, as Cloudflare does by default. A request for a file under `assets/` that is not there must answer 404, never `index.html`: a tab left open across a release asks for code the release removed, and a script answered with HTML fails in ways each browser reports differently, which the router's reload after a failed route load may not recognize. Cloudflare's `single-page-application` fallback answers such a request with `index.html`, as Vite's preview server does; answer `assets/` without it. HSTS is the proxy's to set.

## Organizations

The operator creates organizations, for an account that has signed in once, with the same environment as `serve`; the console creates none unless self-serve is on, below ([ADR 0018](https://github.com/braivo/braivo/blob/main/docs/adr/0018-sign-in-and-invitations.md)):

```bash
bun --no-env-file apps/server/cli/index.ts organization create --name "My School" --slug my-school --owner owner@example.com
bun --no-env-file apps/server/cli/index.ts organization add-member --slug my-school --email learner@example.com
```

`add-member` adds someone who has signed in once, as a learner; `--role author` lets them prepare and publish the organization's content, and `--role admin` also manages its people and settings.

`organization make-owner --slug my-school --email someone@example.com` makes an existing member an owner too, on the organization's instruction, such as when its only owner is leaving: note it in the request's register entry if an erasure needs it. It asks for the slug typed back, as nothing but the database undoes it, and `--yes` skips asking. On a self-serve installation, an owner of any organization cannot set up their own.

**Privacy policy and terms.** `BRAIVO_PRIVACY_URL` and `BRAIVO_TERMS_URL`, absolute http or https URLs to pages you host, add "By continuing, you agree to the Terms and Privacy Policy" under `/login`'s sign-in, where an account is made; set both or neither. Unset, sign-in asks agreement to nothing: set them before inviting anyone beyond a pilot.

**Self-serve.** `BRAIVO_SELF_SERVE_DOMAIN`, a domain such as `braivo.example`, lets anyone signed in who owns no organization set one up in the console, served at `<slug>.<domain>`; one each. It is also how an independent learner gets their own ([ADR 0046](https://github.com/braivo/braivo/blob/main/docs/adr/0046-material-in-steps.md)). Serve the learn app on every subdomain first: wildcard DNS, a wildcard certificate, and a proxy passing `Host`. With it, an AI key needs `BRAIVO_AI_ORGANIZATIONS`, or the server refuses to start. Unset, only the operator creates organizations. Locally, `localhost` serves each at `<slug>.localhost`, as in [the API guide](./api.mdx#an-organizations-domain-locally). `BRAIVO_DATA_REGION`, a region code such as `EU` or `DE`, has setup say the data region, named in each person's language; set it only if the database and files are both there, as Braivo checks neither. `BRAIVO_OTHER_REGIONS` lists the regions other installations serve, making it a choice: `US` shown as coming soon, `US=https://us.example.com` linking whoever chooses it to that installation's `/join` ([ADR 0040](https://github.com/braivo/braivo/blob/main/docs/adr/0040-data-region-at-setup.md)). Before listing an origin, sign in there and set an organization up: Braivo does not check it. Both need `BRAIVO_SELF_SERVE_DOMAIN`; unset, setup says nothing of regions.

### An organization's domain

The learn app presents itself as the organization whose domain serves it, per an `organization_domain` row mapping the hostname to the organization, and Braivo trusts that origin only while the row exists ([ADR 0004](https://github.com/braivo/braivo/blob/main/docs/adr/0004-one-application-origin.md)). The operator registers each with `organization add-domain --slug <slug> --hostname <hostname>`; an organization may have several, named by the latest registered, the earlier still serving, so its `<slug>.<self-serve domain>` stays a way in when its own domain does not work; DNS, TLS, and routing it to Braivo are set up outside Braivo. Learners sign in on the domain's own `/login`, by a code that works there alone; with Google, through `BRAIVO_URL`'s `/login`, which hands the domain a learner session of its own. To try it locally, see [the API guide](./api.mdx#an-organizations-domain-locally).

### Remote MCP clients

AI apps such as ChatGPT and Claude connect at `<BRAIVO_URL>/mcp` by OAuth ([ADR 0045](https://github.com/braivo/braivo/blob/main/docs/adr/0045-remote-mcp.md)), each connection to one organization its person authors in, chosen as they sign in (access-40); what a connection can do is in the [assistants guide](./assistants.mdx). This server accepts a client named by the HTTPS URL of its metadata document (CIMD), fetched only from a public address. It is built for ChatGPT, Claude, and Claude Code; another CIMD client may connect, unsupported. An installation fetching them registers none of the clients below: ChatGPT would sign with a key the registration lacks.

On Workers, `createServer({ clientIdMetadataDocuments: "strictly-public" })` fetches them through the Worker's `fetch`, but only with the `global_fetch_strictly_public` compatibility flag in its configuration; without it, every client named by URL is refused `invalid_client`, since a document's URL on the Worker's own zone would reach the zone's origin, past its security settings. The flag applies to every `fetch` the Worker makes: one to its own zone goes through Cloudflare's public routing, and may reach the Worker again, never the origin directly. To switch from registered clients to fetching, deploy fetching, then at once remove the clients registered below (`oauth-client remove`), since a registration is found before any document; teachers then connect again. Better Auth's limits on fetching documents, and its cache of them, are held by the server, so a Worker building it per request has neither, and any sender could make it fetch from a host of their choosing: it must limit those fetches across requests itself. Either limit `/api/auth/oauth2/*` at the edge, as a request there may fetch a document and its `jwks_uri`, or count the fetches themselves with `wrapClientMetadataFetch`, which wraps each one; the wrapper makes every network request through the fetch it is given, never the global `fetch`, which would skip the refusal of private addresses.

Or a host fetches nothing, with `createServer({ clientIdMetadataDocuments: false })`, accepting only the clients the operator registers, from any machine reaching the installation's database, with its `DATABASE_URL`, `BRAIVO_URL`, and `BETTER_AUTH_SECRET`. On Workers, it is the way back if some client's document cannot be fetched, for every client at once: none named by URL connects unless registered. Registered under their documents' URLs, these connect with a person's sign-in alone, since the host still advertises CIMD and withdraws `private_key_jwt`:

```bash
bun --no-env-file apps/server/cli/index.ts oauth-client add --name ChatGPT --client-id https://chatgpt.com/oauth/client.json --redirect-uri https://chatgpt.com/connector_platform_oauth_redirect
bun --no-env-file apps/server/cli/index.ts oauth-client add --name Claude --client-id https://claude.ai/oauth/mcp-oauth-client-metadata --redirect-uri https://claude.ai/api/mcp/auth_callback
bun --no-env-file apps/server/cli/index.ts oauth-client add --name "Claude Code" --client-id https://claude.ai/oauth/claude-code-client-metadata --redirect-uri http://localhost/callback --redirect-uri http://127.0.0.1/callback
```

The redirect URIs are copied from each document; recheck them there if a client's sign-in fails. Where nothing is fetched, `invalid_client` at sign-in usually means the app sent an ID no `--client-id` registered. Without `--client-id`, `add` prints a random ID, which a person enters in their AI app as their own OAuth client. Each callback takes its own `--redirect-uri`; a loopback one, `http://localhost/callback`, matches any port. `oauth-client remove --client-id <id>` refuses the client's tokens at once, its consents going with it. Where metadata documents are on, a removed client named by URL can sign in again.

### An app directory's reviewer

A directory's review, such as OpenAI's for ChatGPT's, needs an account that signs in without a code ([ADR 0018](https://github.com/braivo/braivo/blob/main/docs/adr/0018-sign-in-and-invitations.md)). Sign in once with an address you read, name the account, and add it to an organization (`organization add-member --role admin`); then list it in `BRAIVO_REVIEWER_EMAILS` and give it a password:

```bash
bun --no-env-file apps/server/cli/index.ts reviewer set-password --email reviewer@fernwood.example
```

It prints a random password once; `--password-stdin` reads one instead, 16 characters or more: a password manager's random one, since only length is checked. The reviewer signs in at `<BRAIVO_URL>/login?method=password`, which nothing links, before connecting their AI app; `/login` reached from a connection takes `&method=password` added too. Afterwards, `reviewer remove-password --email <email>` deletes the password and ends the account's sessions; disconnect its apps in the console (`Connected apps`), and drop the address from `BRAIVO_REVIEWER_EMAILS`.

## Learners' data

The operator exports and erases a learner's data on request, with the same environment as `serve`. Who may ask for which scope, and who receives the file, is [ADR 0053](https://github.com/braivo/braivo/blob/main/docs/adr/0053-learners-data.md)'s.

### Exporting

```bash
bun --no-env-file apps/server/cli/index.ts learner export --email learner@fernwood.example --organization fernwood --out fernwood-learner.json
bun --no-env-file apps/server/cli/index.ts learner export --email learner@fernwood.example --account --out learner-account.json
```

- `--organization <slug>` exports what that school holds, on that school's instruction.
- `--account` exports the account and every school's records of it, on the account holder's own verified request, each school holding records instructing too; it never goes to a school.
- The command reads only, writes nothing to stdout, and creates `--out` readable by you alone, refusing one that exists. Send it over a secure, expiring transfer, then delete it, noting when in the request's register entry. The file is not the whole answer to an access request: purposes, recipients, and retention go with it.

The file is JSON, `version` 1; a change to its format changes `version`. Times are ISO 8601 in UTC. Each organization lists its records oldest first; an account's organizations are ordered by name.

```jsonc
{
  "format": "braivo-learner-export",
  "version": 1,
  "scope": "organization", // or "account"
  "exportedAt": "2026-11-01T09:00:00.000Z",
  "learner": { "name": "Sam Nowak", "email": "learner@fernwood.example" },
  "organizations": [
    {
      "name": "Fernwood School",
      "membership": { "roles": ["member"], "since": "2026-09-01T08:00:00.000Z" }, // null once membership ended, its history kept
      "groups": [{ "name": "Class A English", "role": "learner" }], // or "teacher"
      "attempts": [
        {
          "at": "2026-09-02T10:00:00.000Z",
          // The prompt with a choice task's options (never which is correct) or a typed task's accepted answers; never the explanation.
          "task": {
            "kind": "choice",
            "prompt": "Which greeting fits the morning?",
            "options": ["Good evening", "Good morning"],
          },
          "response": { "choice": 1 }, // an index into options; or { "text": "…" }, or { "reveal": true } for Show answer
          "outcome": "success", // or "failure"; null only if its grade is missing
          "reviewedTeaching": false, // true when the app had shown the learner the objective's passages since their previous attempt on it (ADR 0054)
          // The learner's report of this attempt (ADR 0052), or null.
          "report": {
            "reason": "key-wrong", // or "answer-correct", "confusing", "unsupported", "other"
            "note": "Good day fits too", // or null
            "at": "2026-09-02T10:01:00.000Z",
            "status": "open", // or "dismissed" by a reviewer; "closed" once its task is retired, even after a dismissal
          },
        },
      ],
      "evidence": [
        {
          "at": "2026-09-02T10:00:00.000Z",
          "objective": "Greet someone for the time of day",
          "outcome": "success", // or "failure"
          "origin": "attempt", // or "outside": recorded from a grader elsewhere
        },
      ],
    },
  ],
  // --account alone:
  "account": {
    "createdAt": "2026-09-01T07:55:00.000Z",
    "signInProviders": ["google"], // "google", or "credential" for a reviewer's password; signing in by code adds none
    "connectedApps": [
      {
        "name": "Claude",
        "scopes": ["braivo:author"],
        "connectedAt": "2026-09-03T12:00:00.000Z",
        "updatedAt": "2026-09-03T12:00:00.000Z",
      },
    ],
    "sessions": {
      "console": [
        { "createdAt": "2026-10-30T08:00:00.000Z", "expiresAt": "2026-11-06T08:00:00.000Z" },
      ],
      // Learn domains' sessions record no creation time.
      "learn": [
        {
          "organization": "Fernwood School",
          "hostname": "fernwood.example",
          "expiresAt": "2026-11-06T08:00:00.000Z",
        },
      ],
    },
  },
}
```

### Erasing one school's history

On that school's written instruction, naming the learner and whether their membership ends:

```bash
bun --no-env-file apps/server/cli/index.ts learner erase-history --email learner@fernwood.example --organization fernwood
```

It needs `BRAIVO_ERASURE_LOG` and `BRAIVO_ERASURE_LOG_HMAC_KEY` (below), in addition to `DATABASE_URL`, and refuses to start without them. It shows the database, the account, the organization, and what it will remove, and asks for the slug typed back; `--yes` skips asking, for a script that has shown those already.

- **Removed, at that school alone:** the learner's attempts, evidence, and reports; their learner sessions there, so a learn domain signs them out; their handoffs; sign-in codes and invitations for the address. The account, its console sessions, and other schools' records stay.
- **Membership** is kept, and their next answers start a fresh history. Add `--end-membership` if the instruction says so: their groups go with it, and an organization's only owner is refused.
- **What it leaves behind:** a fence, in `learner_history_state`, so that an old answer resent from an open tab or an integration's retry is refused rather than bringing the history back, even after they leave and rejoin; one record in the log; and any record of invitation mail to the address, which limits mail for a day and is pruned as later mail is sent.
- **Reading its result:** it prints `done` only after the database committed and the log's record says so. "Not confirmed" changed nothing.
- **"The history was erased, but log record … could not be marked done":** the history is gone. Do not run the command again to repair the record: the learner may have practised since, and that is new history. A pending record stays valid for a restore. Note its ID in the request's register entry, and fix the store.
- **An error naming a pending log record and its epoch:** the commit may have gone through unconfirmed, and the counts cannot say, as the learner may have practised since. Run the command again and read its `History` line, typing nothing at the prompt. If it has reached the record's epoch, the erasure committed, so stop, as above. If it has not, confirm: nothing was erased, and the pending record is harmless beside the new one.
- **An error naming no record** erased nothing.

Integrations sending evidence should send the `historyEpoch` a learner's report gives them: without one, a result dated within five minutes after the erasure is refused too.

> [!WARNING]
> Nothing reads the log back yet, so restoring a backup taken before an erasure brings that history back, with an epoch too low to refuse what was refused before, or an erased account back whole (see below). Keep the log. After such a restore, before reopening the service, go through every pending record whatever its date, and every done record whose `doneAt` follows the backup: where the account the command shows has the record's `userId`, and its `History` line is behind the record's `epoch`, run it, with `--end-membership` if that learner's records say so, until the epoch reaches the highest of theirs there. Another account under that email is someone else: type nothing, as what it holds is not the record's to erase. A refusal that no account has the email means the account is absent from the restored database: none of its history is there, but invitations and sign-in codes for the address may have. Remove that school's by hand before reopening; do not create an account to run the command.

### Erasing an account

On the account holder's own verified request, once every school listed has given its instruction ([ADR 0053](https://github.com/braivo/braivo/blob/main/docs/adr/0053-learners-data.md)): this destroys each school's records of them, which no school alone can authorize, and telling a school afterwards is not asking it. Settle any retention exception first.

```bash
bun --no-env-file apps/server/cli/index.ts account erase --email learner@fernwood.example
```

It needs `DATABASE_URL`, `BRAIVO_ERASURE_LOG`, and `BRAIVO_ERASURE_LOG_HMAC_KEY`, and refuses to start without them, or with a blank address. It shows the database, the account and its ID, every school it reaches with their role and practice there, and what it will remove, then asks for the email typed back; `--yes` skips asking, for a script that has shown those already.

- **Removed:** the account, its sessions everywhere, its sign-in methods, its connected AI apps and their tokens, its memberships, groups, and every school's history; its device codes and handoffs; invitations to the address and those it sent; the address's invitation mail claims, so its mail bound starts again; sign-in codes for the address; verification rows naming either.
- **Kept, naming no one:** AI usage counts, so a school's monthly count stays right; a report it dismissed; a setting it changed. Nulling is minimization, not anonymization: in a one-person organization the user is obvious.
- **Out of its reach:** mail already sent. An invitation it sent stays in its recipient's mailbox, naming it, and one still being delivered can arrive after `done`; its link no longer works. Say so in the answer to the request if it matters. Also material a school wrote or uploaded that names the person, a source, its tasks, an objective's title, or an uploaded file: none carries a learner key, and redacting it is separate ([ADR 0053](https://github.com/braivo/braivo/blob/main/docs/adr/0053-learners-data.md)). So never answer that nothing names them; check with each school if the request says it does.
- **An organization's only owner** is refused, nothing erased. On that school's instruction, make its chosen successor an owner first ([`organization make-owner`](#organizations)), adding them with `add-member` if they are not a member yet, and have them sign in to the console and open the school's members before you erase: someone who has only used its learn domain may not know the console. An organization that will not continue under anyone else takes the database: no command closes one.
- **"What holds … changed since it was shown":** a school joined, or the account changed, meanwhile. Nothing was erased; run it again, and check any new school has instructed.
- **"No account has …" and "Nothing to erase":** nothing names that address, as after an earlier run. It succeeds, but it does not prove the person you meant was erased, as the address may be mistyped: read it against the request's register entry.
- **"No account has …" with counts:** rows naming the address remain, such as a code asked for since, or an invitation to an address never registered. Confirm, and they go.
- **Afterwards:** every session and `/mcp` token is refused at once. Signing in again with the address, which anyone holding it may, makes a new account with no history and no membership; only a school adds it again. A school can invite the address again, as any address, and one invited as the erasure commits survives it: run the command again if the request's register entry asks for that certainty, and it shows and removes it.
- **Reading its result:** it prints `done` only after the database committed and the log's record says so. "Not confirmed" changed nothing.
- **"The account was erased, but log record … could not be marked done":** it is gone. A pending record stays valid for a restore. Note its ID in the request's register entry, and fix the store.
- **An error naming a pending log record and an account:** the commit may have gone through unconfirmed. Run the command again and read its `Account` line, typing nothing at the prompt. Showing another ID, the erasure committed, and that is a new account, so stop. Showing that same ID, nothing was erased, so confirm: the pending record is harmless beside the new one. Showing no account, confirm whatever counts it shows, which erases only what still names the address; "Nothing to erase" means it is done.
- **An error naming no record** erased nothing.

> [!WARNING]
> After restoring a backup taken before an account's erasure, before reopening the service, go through the log's `account` records, every pending one and every done one whose `doneAt` follows the backup: where the record's `id` is not in `account_erasure`, and no later record of the same email's `hmac` is, run the command again with the address the request's register names, and read its `Account` line before confirming. Showing the record's `userId`, or no account, confirm. Showing any other account, another ID or any account under a record with no `userId`, stop and settle it by hand against the register: it may be a later registration, as a pending record may never have committed. Leave alone a record whose `id` is there: that backup already holds the erasure, and any row naming the address is someone's since.

## Configuration

`bun run serve` reads its environment alone, never an env file, so the repository's development defaults cannot stand in for a setting a deployment left out; set the variables below in the service's environment, as with systemd's `EnvironmentFile=`. Run the operator's commands with `--no-env-file` too, as shown, or Bun loads those defaults into them ([ADR 0051](https://github.com/braivo/braivo/blob/main/docs/adr/0051-environment-files.md)).

**Origin**

- `BRAIVO_URL`: the public origin serving the console and `/api`, which sign-in callbacks and links are built from; locally, the console's dev server, `http://localhost:5174`, not the server's own port.
- `PORT`: the port the server listens on, 3000 by default.

**Email.** People sign in with a code sent to their email ([ADR 0033](https://github.com/braivo/braivo/blob/main/docs/adr/0033-email-over-smtp.md)).

- `BRAIVO_SMTP_URL`: an SMTP server as `smtps://user:password@host`, or `smtp://`, upgraded with STARTTLS where the server offers it.
- `BRAIVO_MAIL_FROM`: the sender, such as `Braivo <signin@example.com>`.

Unset, codes are written to the server's log, but only while `BRAIVO_URL` is `localhost`, `127.0.0.1`, or `[::1]`, and the server then listens there alone; anywhere else `serve` refuses to start. An address gets one code a minute.

**AI.** Braivo's own drafting and reading of PDFs and photos, for content owners without an AI app of their own ([ADR 0029](https://github.com/braivo/braivo/blob/main/docs/adr/0029-server-drafting.md), [ADR 0030](https://github.com/braivo/braivo/blob/main/docs/adr/0030-server-extraction.md), [ADR 0031](https://github.com/braivo/braivo/blob/main/docs/adr/0031-ai-limits.md)).

- `ANTHROPIC_API_KEY`: enables it. Unset, those routes answer 501, and content owners draft with their own AI apps through `/mcp` ([assistants](./assistants.mdx)).
- `BRAIVO_AI_MODEL`: the model, `claude-sonnet-5` by default.
- `BRAIVO_AI_ORGANIZATIONS`: comma-separated organization IDs allowed to use the key. Unset means every organization, and is refused with `BRAIVO_SELF_SERVE_DOMAIN`; an empty value or `*` is invalid, and the server refuses to start.
- `BRAIVO_AI_MONTHLY_LIMIT`: how many AI requests each organization may make in a calendar month — a count, not a spending cap, since one request costs more than another. Every request is recorded in `ai_request` either way, with its model, prompt version, and how it went; `bun --no-env-file apps/server/cli/index.ts ai report [--since <YYYY-MM-DD>] [--organization <slug>]` counts them.

AI requests may run for up to five minutes, so configure the proxy for that; nginx's `proxy_read_timeout`, for one, defaults to 60 seconds. A request the proxy cuts off may still count toward the organization's limit.

**Google sign-in.** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, an OAuth client from Google Cloud's console, add "Continue with Google" to `/login`; set both or neither. The client's authorized redirect URI is `BRAIVO_URL` followed by `/api/auth/callback/google`, such as `http://localhost:5174/api/auth/callback/google` locally. Only a Google account whose email Google has verified makes or signs in to an account this way ([ADR 0018](https://github.com/braivo/braivo/blob/main/docs/adr/0018-sign-in-and-invitations.md)).

**Reviewers.** `BRAIVO_REVIEWER_EMAILS`, comma-separated, lists the accounts that may sign in with a password the operator set, for an app directory's review (above). Unset, no password signs in.

**Files.** `BRAIVO_FILES` is where uploaded original files, such as the PDFs sources were extracted from, are stored ([ADR 0028](https://github.com/braivo/braivo/blob/main/docs/adr/0028-original-files.md)):

- an absolute path on this machine, or
- `s3://<bucket>` in any S3-compatible store, with `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and `S3_REGION` as Bun's S3 client reads them. For Cloudflare R2, `S3_ENDPOINT=https://<account>.r2.cloudflarestorage.com`; for Google Cloud Storage, `https://storage.googleapis.com` with an HMAC key.

Unset, the installation keeps no files and its file routes answer 501. Braivo accepts original-file uploads up to 50 MB and source requests up to 10 MB. Configure the proxy to accept at least those sizes; nginx's `client_max_body_size` defaults to 1 MB.

**Erasure log.** Only the commands that erase read these ([ADR 0053](https://github.com/braivo/braivo/blob/main/docs/adr/0053-learners-data.md)); `serve` does not. Keep both outside the database and its backups, and apart from `BRAIVO_FILES`, with access only for whoever runs those commands, since each record names a user ID and an HMAC of their email.

- `BRAIVO_ERASURE_LOG`: an absolute path to a directory that already exists, written to disk before anything is erased, or `s3://<bucket>`, with the `S3_*` variables above.
- `BRAIVO_ERASURE_LOG_HMAC_KEY`: the HMAC's secret, at least 32 characters. Keep it for as long as the log: a replay matches email-keyed rows by it.

## These guides

These guides build into a static site of their own, `apps/docs`, which you may publish beside your installation or leave on GitHub, which shows them too. `bun run build` writes it to `apps/docs/dist`; it holds no session and calls no API, so it may share a host with another site, but never the console's or a learn app's origin. Serve it with the headers in its `public/_headers`. On a shared host, send only the base's `docs`, `docs/*`, `guides`, and `guides/*` to `dist/`, such as with more specific Cloudflare routes, and never merge `dist/` into the other site's output: its root `index.html`, `404.html`, and `_headers` for `/*` would replace that site's. For AI tools, each page is also Markdown beside its HTML, such as `guides/faq.md`, indexed by `llms.txt` under the base's `docs`, and all of them in `llms-full.txt` beside it. Three settings, at build, from the environment it runs in rather than an env file:

- `BRAIVO_DOCS_BASE`: the path it sits at, such as `/help/`; `/` by default. Every page, link, image, and its search follow it.
- `BRAIVO_DOCS_BRAND`: the absolute path of a directory to brand it from, in place of `apps/docs/brand/`, outside this repository so updating Braivo never conflicts with it. It holds `site.ts`, whose default export gives the site's `name`, which it must, and optionally a `githubUrl`, `links` for the navigation, and `head`, HTML for every page's head; and `brand.css`, which overrides the theme's `--color-fd-*` colours and fonts. A directory missing either fails the build. Those headers let a page load from and send to the site's own origin alone: bundle a font from `brand.css`, with `url()` to a file in the brand directory, and a font, script, or analytics endpoint elsewhere needs your own headers to allow it.
- `BRAIVO_DOCS_URL`: its public origin, such as `https://docs.example`, without a path. With it, each page names its canonical address, and the build writes `sitemap.xml` at the base; a shared host leaves it unrouted and lists the pages in its own sitemap. Without it, neither.
